# Typical Reasons Extensions Modify Each Metadata Type

Reference lookup for **step 3** ("Group into functional blocks") and **step 2** ("Explain zero-content adoptions") of the main workflow ([../SKILL.md](../SKILL.md)). Each metadata type tends to be touched for a small number of recurring business reasons — knowing them up front speeds up recognizing *why* an object was adopted/changed, without replacing the obligation to read the actual code before writing a conclusion into the report (`SKILL.md` step 4's rule — a pattern name is a starting point, not a conclusion, in every case below too).

Generic and parametrized like the rest of this skill — no example below names a real object, extension, or customer configuration.

---

## Document / Catalog / InformationRegister (data-storage structures) — usually the root elements of a functional block

**Why:** Документы, справочники и регистры сведений — это структуры хранения данных, и именно они, как правило, служат **корневыми элементами** функционального блока: по тому, что именно в них пишется и какие реквизиты/измерения добавлены, определяется, какому блоку принадлежит весь остальной код блока (перехватчики, отчёты, интеграции, механизмы обмена). Внутри этой группы — два разных по сути паттерна изменения:

- **Document/Catalog — автосоздание/зеркалирование при записи.** Несколько типовых документов перехватывают событие записи одинаковой процедурой, которая создаёт/актуализирует запись в другом (обычно собственном) объекте — так реализуется унификация разнородных источников в одну структуру блока.
- **InformationRegister — патч дефицита измерения (теневой/параллельный регистр).** Типовой регистр не поддерживает нужный разрез (например, по организации/юрлицу) — расширение добавляет параллельный «теневой» регистр с недостающим измерением и синхронизирует его с типовым через перехватчик записи.

К коду модулей менеджера и модулей объекта этих типов (документов, справочников, регистров) применимы те же указания по директивам перехвата, что и для `CommonModule` ниже — `&ИзменениеИКонтроль` против `&Перед`/`&После` подсказывают одинаково, где искать функциональную принадлежность правки.

## ExchangePlan (`Content.xml` + registration code) — scoped/filtered replication

**Why:** Основное назначение плана обмена — отслеживание изменений данных справочников/документов/регистров для последующей синхронизации с другой информационной базой. РИБ (распределённая информационная база) — частный случай применения плана обмена, где узлами обмена выступают копии одной и той же конфигурации; типовой план обмена вида `ОбменВРаспределеннойИнформационнойБазе` — механизм БСП, упрощающий именно этот сценарий синхронизации.

Если метаданные входят в состав плана обмена (`Content.xml`) или типовой БСП-код регистрации/фильтрации для плана обмена расширен под конкретный объект — это не отдельная задача сама по себе, а функциональное требование того блока, которому принадлежит объект: «поддержка обмена» для этого объекта/семейства (см. правило шага 3 воркфлоу — не выделять отдельный узел под общий механизм обмена, а описывать его внутри блока-владельца).

## Enum — extending values for a new own classification

**Why:** Новое собственное перечисление принадлежит тому функциональному блоку, в коде которого реально используются ссылки на его значения (какие документы/справочники/запросы его читают), а не блоку, где оно просто объявлено.

Добавление новых значений в уже существующее (в т.ч. типовое) перечисление обычно означает расширение списка допустимых состояний/классификации — нужно искать в коде расширения места, где именно это новое значение сравнивается/читается, чтобы понять функциональную принадлежность. Если ни одного места использования в коде расширения не найдено — это не обязательно мёртвый код: значение могло быть добавлено просто как классификатор в структуре данных (заполняется вручную в форме/реквизите, а не читается программно) — тогда принадлежность определяется по тому, где это значение доступно для выбора, а не по коду.

## DefinedType — composite-type membership growth

**Why:** Определяемый тип (`DefinedType`) в БСП часто служит точкой расширения: типовой обобщённый механизм (обработчик событий, структурная схема, диспетчер) перебирает состав определяемого типа, чтобы понять, к каким объектам применять свою логику, вместо того чтобы явно перечислять типы в коде. Поэтому, когда расширение добавляет свой новый объект в состав уже существующего определяемого типа, оно не создаёт новую логику — оно подключает объект к уже существующему типовому обобщённому механизму. Функционально такое расширение состава принадлежит тому блоку, которому принадлежит сам добавленный объект, а не образует отдельный блок — определяемый тип здесь лишь механизм подключения, как и `ExchangePlan` выше и `ScheduledJob`/`EventSubscription` далее в этом документе.

## Subsystem / Role — placement and rights grants (usually mechanical)

**Why:** Подсистема — это способ показать группу метаданных пользователю в командном интерфейсе, а не сама бизнес-логика:

- **Новая собственная подсистема** обычно означает, что весь набор новых объектов функционального блока нужно вывести отдельным разделом командного интерфейса.
- **Изменение состава `<Content>` уже существующей (типовой) подсистемы** означает включение дополнительных команд/объектов расширения в типовой раздел интерфейса, без создания нового раздела.
- Если объект функционального блока просто присутствует в составе подсистемы без другого связанного кода — это лишь подключение объекта к пользовательскому интерфейсу, а не отдельное функциональное требование; относить объект к блоку нужно по его собственному содержимому, а не по факту нахождения в подсистеме.

Роль устроена аналогично на уровне назначения (не бизнес-логика), но проще: изменение прав обычно чисто механическое — новым/изменённым объектам расширения просто нужен доступ, роль модифицируется только ради этого, без самостоятельного функционального смысла.

Практическое следствие для шага 3 воркфлоу: собственная подсистема — один из первых кандидатов для определения состава функционального блока, поскольку в её `<Content>` обычно собраны именно корневые/ключевые объекты этого блока (документ-реестр, справочники-классификаторы, основные отчёты) — с неё удобно начинать группировку, прежде чем читать код перехватчиков.

## CommonModule — extension-point / dispatcher-hook insertion

**Why:** Общий модуль обычно правится не сам по себе, а как точка входа, через которую расширение либо подменяет фрагмент типового алгоритма, либо добавляет рядом с ним собственную независимую логику. Директива перехвата подсказывает не только где искать функциональную принадлежность правки, но и какой у неё профиль риска при обновлении базовой конфигурации (подтверждено платформенной справкой «Аннотации» / «Инструкции препроцессора»):

- **`&Вместо`** — чистая полная замена: разработчик пишет новое тело с нуля, без обязательства сохранять текст оригинала. Внутри можно (необязательно) вызвать `ПродолжитьВызов()`, чтобы делегировать выполнение исходной типовой реализации — целиком, или до/после собственной логики (обёртка); если `ПродолжитьВызов()` не вызван ни разу — это осознанная полная замена поведения. Платформа **не проверяет** совпадение с текущим типовым кодом при применении расширения — если типовая процедура в базе изменится, расширение продолжит применяться со старой логикой **без предупреждения** (тихое расхождение — самый опасный профиль риска из всех вариантов ниже).
- **`&ИзменениеИКонтроль`** — точечная правка: в новый метод **целиком копируется тело типовой процедуры**, а `#Вставка`/`#Удаление` помечают, что добавлено/удалено. Для применения расширения текст **вне** этих директив обязан совпадать с текущим телом типовой процедуры — если база изменилась, расширение **не применится вовсе**, платформа явно сообщит об ошибке при старте, а не тихо разойдётся. `ПродолжитьВызов()` здесь не используется (и недоступен по правилам платформы) — оригинальная логика уже физически внутри тела, а не вызывается отдельно.
- **`&Перед`/`&После`** — код выполняется до или после типовой процедуры, сама типовая логика не меняется и ничем не рискует при обновлении. Обычно означает добавление самостоятельной, отдельно читаемой бизнес-логики рядом с основным кодом — функциональная принадлежность такой вставки, как правило, видна прямо в её собственном теле, без необходимости анализировать дерево вызовов.

Поскольку в обоих полнозаменяющих вариантах (`&Вместо`, `&ИзменениеИКонтроль`) бизнес-смысл правки явно не выражен самим фактом перехвата (это модификация уже существующей типовой логики), функциональную принадлежность нужно устанавливать по связи с расширяемыми/добавленными метаданными в дереве вызовов — какие объекты реально читает/пишет изменённый код, а не по имени модуля/процедуры.

## Report / DataProcessor with a DCS-only schema — cross-cutting reporting or admin tooling

**Why:** Отчёт или обработка относится к тому функциональному блоку, метаданные которого реально читает её запрос/логика, — а не к блоку, на который лишь похоже название объекта. Появление нового отчёта или обработки обычно прямо следует из функционального требования конкретного блока — нужна отчётность, срез данных или сервисный инструмент именно для него. Отдельный, самостоятельно значимый случай — обработка-обёртка (иногда с частичной подменой) над типовым функционалом: как правило, это прямой признак адаптации под конкретное требование заказчика, а не просто вспомогательный код.

## EventSubscription — hooking a typical event without touching a typical module

**Why:** Подписка на событие — это обработчик, привязанный к паре «тип метаданных + событие», а не самостоятельная бизнес-задача: логика, которую он вызывает, принадлежит тому функциональному блоку, чью потребность она реализует — тот же принцип, что и у `ExchangePlan` выше и `ScheduledJob` далее в этом документе. Частный, но часто встречающийся случай — подписки, регистрирующие изменение объекта в плане обмена (см. «ExchangePlan» выше): такая подписка не отдельная задача, а один из механизмов регистрации в РИБ.

Изменение состава `Источники` уже существующей подписки обычно означает расширение перечня типов метаданных, за которыми должен «следить» обработчик, а не новую логику как таковую.

Появление **новой** подписки добавляет собственный объект `EventSubscription` — но модуль-обработчик, на который она ссылается, часто остаётся типовым и пустым: вся реальная логика уже реализована в базовой конфигурации, подписка лишь связывает событие с ней (см. также шаг 2 воркфлоу — «Explain zero-content adoptions»).

## ScheduledJob — background/periodic execution of an existing action

**Why:** Регламентное задание само по себе не несёт бизнес-логики — это планировщик, который по расписанию вызывает код, реализующий действие, уже принадлежащее какому-то функциональному блоку (то же действие в принципе могло бы быть вызвано вручную, командой или другим событием). Поэтому `ScheduledJob` не образует свой собственный блок — он описывается как часть того блока, чьё действие запускает, той же логикой, что и требование к плану обмена (см. выше «ExchangePlan»): появление регламентного задания в расширении — это сигнал, что конкретное действие данного блока должно выполняться автоматически, по расписанию, без участия пользователя, а не то, что появился новый функциональный блок.
