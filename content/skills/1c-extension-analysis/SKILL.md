# 1C Extension Analysis — Skill Dispatch

Use this skill when the task is **not** to change an extension, but to **understand and document** why it modifies the base configuration — e.g. "analyze this extension and explain why it customizes the typical config", "prepare a report for the customer before a configuration update", "find dead/obsolete adoptions in this extension". For actually *editing* the extension (borrowing, patching, building) use `1c-metadata-manage` (`docs/cfe-manage.md`) instead — this skill is analysis-only and does not write to the extension source tree.

Every configuration and extension is different — this skill and its tools are generic and parametrized (extension path, config path, object name); nothing here is specific to any one customer's standard configuration (ERP, БУХ, УТ, УП, ЗУП, or any other).

**Delegation.** For a full, independent extension audit (the whole workflow below end-to-end, producing the complete report), delegate to the **`1c-extension-analyst`** subagent (`content/agents/extension-analyst.md`, catalog entry in `content/rules/subagents.md`) rather than running the workflow inline — it carries the methodology guardrails (per-child `ObjectBelonging` discipline, completeness-sweep obligation, customer-input-vs-code-fact discipline) that this SKILL.md does not repeat. Run the workflow directly (without delegating) only for a narrow, single-object question (e.g. "why was this one object adopted") where a full report is not the goal.

## Relationship to `1c-metadata-manage` / `cfe-manage`

This skill **builds on top of** `1c-cfe-manage`'s `cfe-diff.py -Mode A`, it does not duplicate it. `cfe-diff -Mode A` already does the single most important and error-prone step correctly: for every object in the extension it classifies `[BORROWED]` vs `[OWN]`, and for borrowed objects it counts **own attrs / own TS / own forms** vs **borrowed items** by descending into `<ChildObjects>` and checking each child's `ObjectBelonging` — not just whether the parent's `<ChildObjects>` tag happens to be open. It also lists every interceptor (`&Перед`/`&После`/`&ИзменениеИКонтроль`/`&Вместо`) per module.

**MCP alternative for a single object — verified working.** `1c-graph-metadata-mcp`'s `compare_base_and_extension(object_name=..., extension_name=...)` gives the same per-object structural diff (attributes/forms/routines added, overridden, unchanged) without needing the source dump on disk — **confirmed correct on 3 known ground-truth cases** in a real analysis (see "MCP usage" below for the full write-up). It uses a genuinely different mechanism than `cfe-diff -Mode A` (a name-based set-diff between two independently-loaded metadata reports, not XML `ObjectBelonging` parsing), and it converged on the same answers both times it was checked against hand-verified findings. **Availability is not guaranteed** — check `.mcp.json` first: this server is not part of every deployment, and even when present it requires a specific setup (one shared Neo4j, `PROJECT_NAME`/`EXTENSION_NAME`/`EXTENSION_BASE_PROJECT` wired correctly — see "MCP usage") rather than the per-tree-isolated pattern used by the other two MCP families in this project. It is still a per-object call, not a whole-extension inventory, so it does not replace step 1 (`cfe-diff -Mode A` for the full object list) — use it to double-check or deep-dive a single object when the graph is populated, and fall back to `cfe-diff`/`reference-finder` (offline, file-based, always available) otherwise.

> **Do not re-derive this by hand with ad hoc `grep`/regex on `<ChildObjects>`.** Treating an open (non-self-closed) `<ChildObjects>` as proof of a new attribute/tabular-section/dimension/resource is the classic mistake this skill exists to prevent — an object's child list is open whenever it contains **any** children, even when every single one is itself `ObjectBelonging=Adopted`. Always run `cfe-diff -Mode A` first and read its own/borrowed counts per object; only fall back to manual XML inspection for a single object when `cfe-diff` cannot run (e.g. `lxml` unavailable) or its output is ambiguous.

## Workflow

1. **Inventory** — run `cfe-diff -Mode A` (see `content/skills/1c-metadata-manage/docs/cfe-manage.md`) against the extension and its base configuration source. This gives the full object list, `[BORROWED]`/`[OWN]` split, own-vs-borrowed child counts, and interceptor list in one pass.

   **Build a change registry, not just an object list — one row per atomic change, not per object.** An object is not the right unit of analysis: a single object routinely carries several independent changes (own attributes, own forms, several interceptors, each doing something unrelated to the others). Track every own attribute / own tabular section / own form / interceptor / exported procedure as its own row (`Объект | Механизм | Куда пишет/что читает | Блок`), leaving `Блок` empty until step 3 fills it in. This is what catches a case like a document that carries both a uniform "auto-create a registry entry" interceptor (block A) *and* its own attributes plus a second, unrelated interceptor feeding a completely different register (block B) — assigning the whole object to block A on the strength of the first interceptor found would silently drop block B's requirement.

   **Generate the registry from the source tree, not from a search for an already-known pattern name.** A pattern-first search (e.g. `bsl_find_symbol("ИК_ПриЗаписи")`) can only ever surface what it already went looking for — it structurally cannot find a sibling object's *differently-named* second interceptor, because nobody had a reason to search for that name. Confirmed independently on the same real extension by three separate analysis passes, including one built on structural symbol search: all three missed the same second interceptor on the same document (and one of them, on a sibling document too), because each started from a known name and asked "who else has this" instead of asking "what does this specific object actually own". Run **`registry-builder`** ([docs/registry-builder.md](docs/registry-builder.md)) — it walks the extension tree directly (same `ObjectBelonging`/interceptor-scanning logic as `cfe-diff -Mode A`, self-contained per this skill's convention) and emits one row per own attribute/tabular section/interceptor/own-form-routine with `Блок` left empty, so nothing gets into the registry only because someone thought to search for it. Use `-CompareAgainst <already-written-report.md>` to get a coverage check against a draft report — treat its output as "not even mentioned" evidence, not as a strict per-mechanism diff (see the tool's own "Known gaps" for exactly what it does and does not prove).

   **Dispatcher decomposition — when one procedure is itself a multi-block dispatcher.** If a single procedure's body contains **more than one** `Если`/`ИначеЕсли` branch comparing against metadata identity or type (`ОбъектМетаданных = Метаданные.X.Y`, `ТипЗнч(...) = Тип(...)`), one registry row for "the procedure" is not enough — confirmed case: a single 500+-line dispatcher procedure carried ~50 branches for one functional block plus 2 explicit branches (with their own justifying comment) for a completely different block. `registry-builder` flags this automatically (`DISPATCHER` rows, with a branch count) — it cannot classify the branches itself, only tell you a routine needs the following treatment: decompose to branch level, but **group by unique shape (same block + same mechanism), not by literal branch count** — a row per distinct combination is enough; do not produce dozens of near-duplicate rows for branches that only differ by which metadata type they name. **Treat a registry row that groups an unusually large number of branches under one `Блок` value as a signal to double-check for a hidden second block** — a rule stated only as "don't lump a shared dispatcher into one block" is easy to skip silently; a visibly oversized row in the artifact itself is not. This does not catch every possible case (a branch could still hide a further sub-distinction), but it is a large, mechanically-triggerable improvement over object-level or procedure-level granularity, and is a pragmatic stopping point rather than an exhaustive guarantee.
2. **Explain zero-content adoptions** — for every `[BORROWED]` object with zero own attrs/TS/forms/interceptors, run the **reference finder** ([docs/reference-finder.md](docs/reference-finder.md)) to find the technical reason it was adopted (composite-type reference vs. code/query reference) or confirm it has none (candidate for exclusion).
3. **Group into functional blocks** — objects that are `[OWN]` (fully new) or `[BORROWED]` with real own content rarely stand alone; group them by the business scenario they implement (e.g. "outgoing document registry", "personal-cabinet integration", "RIB exchange"). This step is currently manual — read the code, follow cross-references, use the project's `1c-graph-metadata-mcp` tools (`get_object_dossier`, `trace_impact`, `search_code`) per `content/rules/tooling-playbooks.md`. For form-layout questions specifically, prefer the offline `1c-form-info` tool (see "MCP usage" below) over any MCP form-layout call.

   **Before reading code from scratch, check [docs/metadata-modification-patterns.md](docs/metadata-modification-patterns.md)** — a reference of the recurring reasons each metadata type tends to get touched (e.g. an `InformationRegister` gaining a dimension-gap shadow copy, an `ExchangePlan` getting scoped/filtered replication, a `DefinedType` growing to cover a new own object). It speeds up recognizing *why* an object was likely adopted/changed — it does not replace reading the object's actual code before writing the reason into the report.

   **For every wholly-new `Report`/`DataProcessor` with an SKD-only schema (no `ObjectModule`/`ManagerModule` code), read its DCS query — or run `dcs-query-fields-extractor`** ([docs/dcs-query-fields-extractor.md](docs/dcs-query-fields-extractor.md)) **— *before* assigning it to a functional block.** Confirmed failure mode (see that doc's Provenance for the exact case): a wholly-new report was grouped by one analysis into the same block as unrelated objects purely because of a shared name suffix, without reading its query — which actually aggregated unrelated data and had nothing to do with those objects. Group by what the query actually reads, not by name similarity with other objects in the extension.

   **Exchange-plan / RIB participation is a requirement of the owning block, not a separate infrastructure block.** When an object already belongs to a functional block by its own business purpose, and that same object also participates in an exchange plan — listed in `Ext/Content.xml`, or registered/filtered by code (a registration-rules handler, a hardcoded dispatcher, a registration-settings helper) — describe that participation as part of *that block's* requirements. Do not carve out a standalone "exchange mechanism" / "RIB filter" node to hold it, even when the registration code is physically shared across several blocks (one dispatcher, one common registration-settings module). Confirmed failure mode: an earlier pass on a real extension grouped every RIB-registration finding into one artificial cross-cutting block, reasoning that "the code lives in one shared module" — but a closer read showed each block's objects actually had their own, separately describable registration path (one block registered through a dedicated insertion into the typical registration-settings channel; another block registered exclusively through a shared fallback dispatcher, but the dispatcher's branches for that block's objects were still fully attributable to it, including their own version-marker history). Splitting a shared mechanism's description across the blocks it actually serves — instead of centralizing it in an artificial node — keeps every requirement traceable to the business need that created it, and lets each block's update risk be assessed on its own evidence instead of one blended risk statement. The **only** thing that legitimately stays a cross-cutting note instead of living inside a block is the shared mechanism's own recurring-maintenance risk, and only when there is concrete evidence for it (e.g. version-marker comments proving the mechanism has already been revised more than once) — record that in the report's risk section (see skeleton §7 below), not as its own functional-block subsection.
4. **Find uniform code patterns** — when several documents/objects look like they implement the same customization independently, search for a shared signature (a region name, a distinctive procedure name) across all `ManagerModule.bsl`/`ObjectModule.bsl` files to confirm the pattern is genuinely uniform and to catch any object that implements it but was missed in step 3. If `onec-hbk-bsl-*` (or an equivalent BSL symbol-index MCP) is exposed, prefer `bsl_find_symbol(name=..., limit=<enough to cover every hit>)` over `Grep` for this — it returns every definition of a same-named procedure across the whole workspace with exact `file_path`/`line` in one structured call, instead of a text match you still have to de-duplicate by hand. **Either way, a matching interceptor/procedure name is a starting point, not a conclusion** — read the actual body of every matched object before asserting they all share the implementation. Confirmed failure mode: a large group of sibling documents shared an identical interceptor name, and one of them turned out to call a completely different (and broken) mechanism than the rest — a report that grouped by name alone missed the outlier and, worse, went on to claim "no enum-reference discrepancies found" a few sections later, directly contradicted by the one unread body (see `enum-value-checker.md`'s Provenance for that exact bug). Enumerating candidates is not the same as confirming they are the same pattern — only reading each body does that.
5. **Completeness sweep before writing conclusions** — cross-check every object that has *any* `Ext` subfolder (real code/forms/templates) against what step 3 already classified. `bsl_meta_collection(collection="Справочники" | "Документы" | ...)` (if exposed) gives a fast one-call inventory per metadata type to check nothing was missed — confirmed to match a manual `Configuration.xml` count exactly. Do not declare the analysis complete on the strength of "the customer described N reasons" alone — enumerate every object with real content and make sure each one lands in a named block, a "confirmed no effect" note, or an explicit open question. This is the step that most often finds forgotten reports, disabled data processors, and orphaned print templates.

   **The closure gate is the change registry's `Блок` column, not the object list.** "Every object landed somewhere" is not sufficient — walk every row of step 1's change registry and confirm `Блок` is filled (or explicitly marked unassigned, per report skeleton §7 below) before the analysis counts as complete. An object with all-but-one of its rows assigned is not "done" — the one empty row is exactly the kind of thing this gate exists to catch.

   **Run the semantic-bug sweep before writing conclusions, not instead of reading code.** A full line-by-line reading pass does not scale to hundreds of objects, and a `grep`-scale pass over the same tree misses semantic defects that still parse as valid BSL — confirmed in practice: a `grep`-driven completeness pass on a real extension found none of several confirmed bugs even though every affected file was "read" (see each tool's own Provenance section below for the exact cases). Run the four narrow checkers over the whole extension tree as a mechanical supplement:

   - `1c-enum-value-checker` — enum-value literals referencing a value the enum does not have.
   - `1c-defined-type-dispatch-checker` — per suspected dispatch routine, a `DefinedType` member not handled by any branch.
   - `1c-broken-metadata-path-checker` — hardcoded `"Тип.Имя.Форма..."` literals referencing an object that does not exist.
   - `1c-dead-code-after-insert-checker` — a top-level unconditional `Возврат` shadowing typical code or the extension's own code that follows it.

   Every finding is still a candidate, not an automatic report entry — confirm each one against the actual source before writing it into section 2 or 4, same as any other finding in this workflow.
6. **Write the report** using the section skeleton below.

## Report skeleton

A finished analysis is a single Markdown file with these sections, in order:

| # | Section | Content |
|---|---|---|
| 0 | Исходные данные от заказчика | Verbatim customer input, numbered as given |
| 1 | Общие сведения о расширении + Метод анализа | Configuration/extension identity, platform version, and an explicit methodology note (what "adopted" vs "own" means, per-child `ObjectBelonging`, not just open `ChildObjects`) |
| 2 | Функциональные блоки и причины модификации | One numbered subsection per functional block found in step 3; dedicate a subsection to any single object worth a deep dive; flag obsolete/candidate-for-removal findings explicitly in the subsection title. If a block's own objects participate in an exchange plan (RIB or otherwise), describe that as a named part of *this* subsection (e.g. an "exchange mechanism" paragraph) — do not create a separate cross-block subsection for it (see step 3's exchange-plan rule) |
| 3 | Сводная таблица изменённых объектов | One row group per object type, cross-referencing the relevant `2.x` subsection |
| 4 | Не подтверждено / требует уточнения у автора расширения | Every object adopted with zero real content, with its reference-finder verdict; use blockquotes to record items that started here and were later closed |
| 5 | Вопросы к заказчику для следующего раунда обсуждения | Only genuinely open questions — a question closed by evidence found later in the same session must be moved into a blockquote here (or into the relevant `2.x`/`4` section) and removed from the numbered list; renumber after every removal |
| 6 | Итоговый вывод | The functional blocks restated as a short list, isolated additions, confirmed-obsolete items, corrections to earlier (wrong) claims |
| 7 | Риски и опасения заказчика при обновлении типовой конфигурации | Only genuine update-time risks, tied to specific objects/mechanisms found in section 2 |

Keep sections 4 and 5 honest: an item stays in "open questions" only while it is genuinely unresolved. As soon as code/reference evidence closes it, move the resolution into the relevant numbered section and strike it from section 5 — do not leave a question in section 5 that the analysis itself has already answered.

**Appendix — change registry.** Include step 1's change registry (`Объект | Механизм | Куда пишет/что читает | Блок`) as a report appendix, not just scratch working material — it is the evidence trail that shows every atomic change was actually accounted for, and lets a reader audit section 2's block assignments against the underlying granular facts instead of taking them on faith. Keep rows collapsed by unique shape (per step 1's dispatcher-decomposition rule) — the appendix should stay a few dozen rows for a mid-sized extension, not hundreds.

**Adopted-object staleness — read before trusting a "declared value" / "composition" result from `1c-enum-value-checker` or `1c-defined-type-dispatch-checker`.** An extension's own copy of an `Adopted` (typical) object can be a stale snapshot with far fewer children than the base configuration currently declares — confirmed in practice for both an `Enum` and a `DefinedType` on the same real extension (see each tool's own doc, "Adopted ... resolution" / Provenance, for the case that surfaced this). Both tools resolve this by preferring the base configuration's copy over the extension's own snapshot whenever `-ConfigPath` is given and the object is `Adopted` — **always pass `-ConfigPath` to these two tools**; running without it is a degraded, unverified mode.

## Environment constraints — tool availability is not guaranteed

Both `cfe-diff` and `1c-reference-finder` are Python scripts that need a shell to run. **Confirmed in this project: a subagent invocation can end up with only `Read`/`Write`/`Edit`/`Grep`/`Glob` available, with no working shell and no MCP tools, even when the invoking agent's own configuration lists `Bash`/`MCP` among its tools.** Check for a working shell at the very start of a run (attempt a trivial command) rather than assuming it and discovering the failure mid-workflow. If no shell is available:

- Do the per-child `ObjectBelonging` check from step 1 by direct `Read`/`Grep` of the metadata XML (same logic `cfe-diff -Mode A` implements — see `content/skills/1c-metadata-manage/tools/1c-cfe-manage/scripts/cfe-diff.py` for the exact algorithm if in doubt).
- Do the reference search from step 2 by `Grep` for the object's Ref-type token and manager/query-style Cyrillic name across the extension tree (same logic `reference-finder.py` implements — see [docs/reference-finder.md](docs/reference-finder.md)).
- State plainly in the report's methodology section (section 1) that the check was performed manually because no shell tool was available, not because of a missing Python dependency — these are different failure modes and the report should not conflate them.

## MCP usage

This is analysis work, not a BSL/metadata edit — the verification-checklist BSL validators (`syntaxcheck`/`check_1c_code`/`review_1c_code`) do not apply. Use the project's search/graph MCP tools (`content/skills/mcp-1c-tools/SKILL.md`, `content/rules/mcp-first-search.md`) for step 3 (grouping into functional blocks) and to verify claims about base-configuration behavior before writing them into the report, per `content/rules/sdd-integrations.md`'s evidence discipline — every metadata name, attribute, or platform behavior asserted in the report should be grounded in a source you actually checked, not assumed from a similar-looking object.

### `onec-hbk-bsl-*` BSL static-analysis MCP servers — verified capabilities and pitfalls

Some projects expose a BSL language-server-backed MCP pair, one instance per workspace root (e.g. `onec-hbk-bsl-main` over the base config, `onec-hbk-bsl-ext` over the extension) — check `.mcp.json` for the exact server names. This pairing is architecturally well-suited to extension-vs-base comparison, but each tool was **empirically tested against known ground truth** from a real analysis before being trusted here — the results are mixed. Do not assume tool descriptions alone; the two findings below were only caught by cross-checking against XML actually read by hand.

**Genuinely useful, verified:**

- **`bsl_find_symbol(name, limit)`** — returns every definition of a same-named procedure/function across the whole workspace with exact `file_path`/`line`. Confirmed: found every definition of a shared interceptor name in one call, including the one outlier with a different implementation (see the Workflow step 4 case and `enum-value-checker.md`'s Provenance). **This is the correct tool for step 4's "read the actual body of every matched object" requirement** — enumerate with `bsl_find_symbol` first, then read each file it lists.
- **`bsl_meta_collection(collection, limit)`** — one-call inventory of every object in a metadata collection (`"Справочники"`, `"Документы"`, `"РегистрыСведений"`, …). Confirmed: returned every object in a collection, exactly matching a manual `Configuration.xml` count. Good for step 5's completeness sweep.
- **`bsl_diagnostics(file_path, include_unused=true)`** — a real BSLLS-compatible diagnostic engine, including a `BSL-DEAD` (unused non-export routine) check. Useful as a fast first-pass scan across many modules before manual reading — but treat `BSL-DEAD` hits on interceptor procedures (`&Перед`/`&После`/`&ИзменениеИКонтроль` targets) as needing verification, not fact: the engine may not recognize a directive-bound interceptor as "used" and can false-positive there.
- **`bsl_status`** — trivial index-readiness check, run first.

**`BSL051` (`UnreachableCode`) — verified partial overlap with `1c-dead-code-after-insert-checker`; run both, do not treat either as a substitute for the other.** Tested against every confirmed dead-code finding from that tool on a real extension: `BSL051` correctly fires when the unreachable code sits in an otherwise plain routine with no `#Вставка`/`#КонецВставки` markers, but returns **zero** diagnostics when the unreachable code is typical/original logic left dangling right after a `#КонецВставки` marker — the analyzer appears to treat the `#Вставка`/`#КонецВставки` boundary as breaking its control-flow graph, even though the platform executes the code on both sides as one plain statement sequence at runtime. On exactly those missed cases, `include_unused=true` only produces a `BSL-DEAD` "unused function" hit instead — a **different and misleading** signal (the routine is not unused, it is a directive-bound interceptor; see the already-documented `BSL-DEAD` false-positive class two bullets above) that does not communicate "there is dead code inside this actively-used routine" at all. This is exactly the highest-value case for this skill (typical behaviour silently shadowed by an extension), so `1c-dead-code-after-insert-checker` ([docs/dead-code-after-insert-checker.md](docs/dead-code-after-insert-checker.md), see its Provenance for the exact tested cases) is not redundant with `BSL051` — run both; `BSL051` is the faster first pass, the offline tool is the one that reliably covers the `#Вставка`-adjacent case.

**No BSL-LS rule overlaps `1c-enum-value-checker`, `1c-defined-type-dispatch-checker`, or `1c-broken-metadata-path-checker` — verified.** Ran full `bsl_diagnostics(include_unused=true)` against the real file carrying each tool's confirmed bug (see each tool's own doc, "Relationship to BSL-LS / MCP diagnostics" and Provenance, for the results) — none of the ~180 public rules (`bsl_list_rules`) fired on any of the three; the engine has no notion of enum-value existence, `DefinedType` composition completeness, or metadata-path string validity. `1c-syntax-checker-mcp`'s `syntaxcheck` cannot cover these either — it takes a bare code string with no workspace/metadata context, so it cannot resolve enum values, `DefinedType` members, or object existence in the first place. All three tools are additive, not overlapping.

**Confirmed unreliable for this skill's core methodology — do not use as a substitute:**

- **`bsl_meta_object(name)` does NOT distinguish `ObjectBelonging=Adopted` from own attributes.** Verified directly: queried against a catalog known (from a line-by-line XML check) to have only `Adopted` attributes, it returned the same attribute list with no adoption flag either way. Querying the identical object against the *base configuration's own* index (`onec-hbk-bsl-main`) returned the exact same attribute list — proving the tool reports the object's structure as such, with no per-child `ObjectBelonging` filtering at all. **Using this tool in place of `cfe-diff -Mode A` / the per-child `ObjectBelonging` check would silently reintroduce the exact "open `ChildObjects` ≠ new attribute" mistake this skill exists to prevent.** It may still be useful for a quick shape overview, but never cite its attribute list as evidence of what the extension added.
- **`bsl_references(symbol_name)` only indexes BSL code, not XML metadata type declarations.** Verified: run against an object known to have several genuine composite-type references inside other objects' XML (`CatalogRef.X` in dimension/attribute `<Type>` elements), it returned `reference_count: 0`. It cannot see the "composite-type reference" mechanism from `content/skills/1c-extension-analysis/docs/reference-finder.md` at all — at most it can supplement the "code/query reference" half, and only for BSL text, not embedded DCS query XML either (untested, treat as unconfirmed).
- **`bsl_callers`/`bsl_callees(symbol_name)` resolve to a single arbitrary definition when multiple modules share a procedure name**, unlike `bsl_find_symbol`. Verified: called on a procedure name shared by many modules, it picked one file and reported zero callers, silently ignoring the rest. Do not use these two for a name shared across modules until you have first disambiguated with `bsl_find_symbol` — and even then, the tools take a symbol name, not a file path, so there is no confirmed way to scope the query to one specific definition.

Net effect: this MCP pair is a genuine accelerant for steps 4 and 5 (pattern enumeration, collection inventory, fast dead-code scanning) but **does not replace** `cfe-diff -Mode A` / `reference-finder.py` for steps 1–2 (the `ObjectBelonging` and reference-mechanism checks) — those remain the authoritative source for "was this added by the extension" questions.

### `1c-code-metadata-mcp` — removed from this project's stack; use `1c-form-info` instead

This server (`comol/1c_code_metadata_mcp`) has been **removed** from this project's `docker/docker-compose.yml` and is no longer part of this deployment's toolset. Do not stand it back up or route step 3/5 through it. Its findings, kept here only because another deployment of this skill might still expose it:

- **Cannot answer `ObjectBelonging` no matter how it's scoped.** `get_metadata_details(...)`, queried against an instance correctly bind-mounted to the extension source alone, still returned the object's full attribute list with no adoption flag — independently confirmed to be entirely `Adopted` (typical) attributes by direct XML reading. `cfe-diff -Mode A` / the per-child `ObjectBelonging` check remain the only authoritative source for "did the extension add this".
- **Its one function not otherwise duplicated by the graph server — `inspect_form_layout` (form element tree, attributes, commands, handlers) — is fully replaced by the offline `1c-form-info` tool** (`content/skills/1c-metadata-manage/tools/1c-form-info/scripts/form-info.py`, documented in `content/skills/1c-metadata-manage/docs/form-manage.md`). Reading the server's own source (`form_index.py`) showed it parses `Form.xml` with stdlib `ElementTree` (no embedding involved at all for this call) but calls `handler.getparent()` — an `lxml`-only method — to attach each event handler to its owning element; since `ElementTree` elements have no such method, `element_name` in its output was always empty. `form-info.py` reads events directly off each element node (uses `lxml`) and does not have this defect, plus it renders a real element hierarchy, typed attributes, and form commands/parameters that the MCP tool's flat JSON did not. Use `form-info.py` directly for any form-layout question in this skill's workflow — no container, no embedding backend, runs in seconds.

### `1c-graph-metadata-mcp` — `compare_base_and_extension` verified correct, but needs a specific shared-DB setup

Unlike `onec-hbk-bsl-*` and `1c-code-metadata-mcp`, this server is **not** meant to run as two fully isolated per-tree instances for extension-vs-base work — its cross-config comparison tools only work when both trees are loaded into **one shared Neo4j**. This was not obvious from the tool description alone; the exact mechanism is documented in the image's own bundled OpenSpec archive (`/app/openspec/changes/archive/*-add-extension-support/`, readable via `docker compose exec <service> cat ...` on the container) and confirmed by standing up the shared setup and testing it.

**Setup, confirmed working:**

- One `neo4j_graph` container backs **two** `1c_graph_metadata_mcp` app instances (base and extension), both pointed at the same `NEO4J_URI` — not one Neo4j per tree.
- Base instance: `PROJECT_NAME=<any distinct label>` — the scoping tag other tools can filter on via their optional `project_name` parameter.
- Extension instance: `EXTENSION_NAME=<extension's own name>` + `EXTENSION_BASE_PROJECT=<must exactly match the base instance's PROJECT_NAME>`. Setting these marks every loaded node `origin="extension"` and, after its own metadata load finishes, runs a background task (`extension_relationships`) that builds `EXTENDS`(modified) and `OVERRIDES`(Form/Module/Routine) edges against the base project's nodes. Without both variables set, this task is silently `skipped` (visible via `get_indexing_status`) and `compare_base_and_extension` has nothing to compare against.

**Discovery-first — never guess `extension_name`/`project_name`.** Confirmed failure mode: a call to `search_metadata({"operation": "list_extension_objects", "extension_name": "<a plausible-looking name>"})` silently returned nothing, because the guessed name did not match this session's actual configured `EXTENSION_NAME` — the call looked like a legitimate attempt but was really unverified input. `get_indexing_status` (or the equivalent status call on whichever graph server is exposed) typically echoes back the actual configured project/extension names it indexed under — call that first and use the exact value it reports, never a name you inferred from the extension's directory/display name. If no discovery call is available, check `.mcp.json` / the server's environment configuration directly, or ask the user, rather than substituting a guess — this is the same "no blind chaining" discipline from `AGENTS.md → MCP Tool Calling`, applied specifically to this server's free-text identity parameters.
- Both instances need the env var `METADATA_DIRECTORY` (not `METADATA_PATH` — that name is only correct for `1c-code-metadata-mcp`), pointed at a directory containing one or more `.txt` "Отчёт по конфигурации" exports (Configurator → Конфигурация → Отчёт по конфигурации). The XML source dump the other two MCP families use is not sufficient here; a missing directory or a directory with zero `.txt` files makes the container abort on startup (crash-loop) — no graceful degradation.
- Loading a real base configuration's report (a large text export, several thousand objects) took double-digit minutes end-to-end for structural/metadata/fulltext/BSL-graph indexing, plus a much longer offline-CPU-fallback pass for routine-level embeddings (well over 100k routines) when the configured OpenAI-compatible embedding endpoint returned 404 for the requested model — check `get_indexing_status` rather than assuming a fixed duration; `any_running: false` is the authoritative "done" signal, not elapsed wall-clock time.
- Chroma-style volumes are unnecessary for this server (unlike `1c-code-metadata-mcp`, which genuinely uses them) — everything, including vector indexes, lives in Neo4j. Do not carry over the `chroma_db` volume mount from the `1c-code-metadata-mcp` compose blocks by copy-paste; it stays empty.

**`compare_base_and_extension(object_name, extension_name)` — verified correct on 3 ground-truth cases:**

- A document known (from independent manual analysis) to have a genuinely new, non-overriding procedure with the same name as a routine shared by many sibling documents: the tool correctly listed every attribute as "из базы" (extension added none) and the procedure as **"Добавлены"** (added, not an override) — matching the manually-confirmed finding exactly.
- A catalog independently confirmed (via `reference-finder.py` + manual per-child `ObjectBelonging` reading) to be adopted with zero own content, zero references anywhere — the tool returned every attribute as "из базы", no form overrides, and `(нет процедур)` — i.e. a clean, fully-empty diff, consistent with "candidate for exclusion".
- `search_metadata({"operation": "list_extension_objects", "extension_name": ..., "extends_type": "added"})` returned a set of genuinely new top-level objects (no base counterpart at all) — integration common modules, event subscriptions, new registers/catalogs/reports — matching the extension's already-understood functional footprint, cleanly separated from a much larger set of merely-adopted (`EXTENDS(modified)`) objects.

Unlike `bsl_meta_object`/`get_metadata_details` (confirmed blind to `ObjectBelonging` — see above), `compare_base_and_extension` does **not** rely on reading an `ObjectBelonging` flag at all: it independently loads the base's and the extension's metadata reports as two separate node sets and computes a plain name-based set difference. That is a genuinely different mechanism from `cfe-diff -Mode A`'s XML-attribute reading, which is exactly why cross-checking the two against each other is worthwhile — they can fail independently, and so far they have agreed on every case tested.

**Known scope limits (not yet tested, treat as unconfirmed):** the tool's own scenarios only cover Реквизиты/Формы/Процедуры-функции — roles, RLS, subsystem composition, and command-interface changes are outside what it compares, same gap `reference-finder.py` already documents for itself. An empty "Формы" section for one object says nothing about form overrides elsewhere in the extension — step 5's completeness sweep is still mandatory regardless of this tool's availability.
