# 1C Extension Analysis — Skill Dispatch

Use this skill when the task is **not** to change an extension, but to **understand and document** why it modifies the base configuration — e.g. "analyze this extension and explain why it customizes the typical config", "prepare a report for the customer before a configuration update", "find dead/obsolete adoptions in this extension". For actually *editing* the extension (borrowing, patching, building) use `1c-metadata-manage` (`docs/cfe-manage.md`) instead — this skill is analysis-only and does not write to the extension source tree.

**What this skill is validated on.** Its rules come from repeated audits of **one** extension, so the reasoning is tested and the coverage is not: the traps described below are real and the list of them is certainly incomplete. Figures that merely calibrated that one case have been removed on purpose — if a count here differs on your extension, that is expected and not a signal. What should hold anywhere is the shape of each trap, the tool contracts, and the three closure gates. Where a rule presupposes `&ИзменениеИКонтроль`, an exchange plan or an XML dump of both trees, the preconditions section says so; treat anything else as a hypothesis you are the first to test, and report in the limits section which checks did not apply.

Every configuration and extension is different — this skill and its tools are generic and parametrized (extension path, config path, object name); nothing here is specific to any one customer's standard configuration (ERP, БУХ, УТ, УП, ЗУП, or any other).

**Delegation.** A full audit belongs to the `1c-extension-analyst` subagent (`content/agents/extension-analyst.md`); run the workflow inline only for a narrow single-object question. If you *are* that subagent, this note is not for you — proceed.

**Methodology.** Read [docs/methodology.md](docs/methodology.md) before the first step, delegated or inline — per-child `ObjectBelonging`, the completeness sweep, customer input vs. code fact, the `CONFUSION`-vs-open-question line and the report discipline. This file does not repeat them.

## Relationship to `1c-metadata-manage` / `cfe-manage`

This skill **builds on top of** `1c-cfe-manage`'s `cfe-diff.py -Mode A`, it does not duplicate it. `cfe-diff -Mode A` already does the single most important and error-prone step correctly: for every object in the extension it classifies `[BORROWED]` vs `[OWN]`, and for borrowed objects it counts **own children of every kind** (attributes, tabular sections, forms, templates, commands, enum values, dimensions, resources …) vs **borrowed items** by descending into `<ChildObjects>` and checking each child's `ObjectBelonging` — not just whether the parent's `<ChildObjects>` tag happens to be open. A child serialized as a bare name (a form, a template, a nested subsystem) has no `<Properties>` there; its ownership is read from its own descriptor file. It also lists every interceptor (`&Перед`/`&После`/`&ИзменениеИКонтроль`/`&Вместо`) per module.

What an adopted object changes outside `<ChildObjects>` is listed too: the platform marks each such property in `<xr:PropertyState>` (`Type` of a defined type, `Rights` of a role, `Predefined`, `CommandInterface`, `Template`, `Form`, an exchange plan's `Content`), and cfe-diff prints it with its detail — the added types, the objects granted, the own predefined items. An adopted subsystem's added `Content` is printed separately: the platform does not mark it. For each borrowed form, the own attributes, commands and layout elements and the elements whose own properties changed are taken from the difference against the `<BaseForm>` snapshot in the same `Form.xml`. The run ends with `=== Unclassified files: N ===`: every file of the extension that no line above interpreted. Anything but 0 is a construct no tool has read yet — read those files before calling the inventory complete.

**MCP alternative for a single object.** `1c-graph-metadata-mcp`'s `compare_base_and_extension(object_name=..., extension_name=...)` gives the same per-object structural diff (attributes/forms/routines added, overridden, unchanged) without needing the source dump on disk. It compares the base and extension layers by name instead of parsing XML `ObjectBelonging`, so it fails independently of `cfe-diff -Mode A` — which is what makes it a useful cross-check. The server is not part of every deployment — check `.mcp.json`; setup and extension layers: `content/skills/mcp-1c-tools/docs/1c-graph-metadata-mcp.md`. It is a per-object call, not a whole-extension inventory, so it does not replace step 1 (`cfe-diff -Mode A` for the full object list) — use it to double-check or deep-dive a single object, and fall back to `cfe-diff`/`reference-finder` (offline, file-based, always available) otherwise.

> **Do not re-derive this by hand with ad hoc `grep`/regex on `<ChildObjects>`.** Treating an open (non-self-closed) `<ChildObjects>` as proof of a new attribute/tabular-section/dimension/resource is the classic mistake this skill exists to prevent — an object's child list is open whenever it contains **any** children, even when every single one is itself `ObjectBelonging=Adopted`. Always run `cfe-diff -Mode A` first and read its own/borrowed counts per object; only fall back to manual XML inspection for a single object when `cfe-diff` cannot run (e.g. `lxml` unavailable) or its output is ambiguous.

## Workflow

1. **Inventory** — two sources, and they disagree in known ways, so take each for what it is good at.

 **Top-level object list and the adopted/own split — `search_metadata` with `{"operation": "list_extension_objects", "extension_name": "<layer>"}`.** Every row carries `extends_type` (`added` / `modified`) and, for a modified one, its `base_object_name`. Measured 2026-09-29 against the files: the graph returned exactly the count the source tree has, and split it exactly as `ObjectBelonging` does. Filtering by `extends_type: "adopted"` returns nothing; the vocabulary is `added` / `modified`.

 **Own-vs-borrowed child counts, extended properties and the interceptor list — `cfe-diff -Mode A`** (`content/skills/1c-metadata-manage/docs/cfe-manage.md`). The graph operation above stops at the top level; this is what counts a given object's own children of every kind against its borrowed ones, lists what it changes outside them and the annotations per module, and closes with the `Unclassified files` count. Its `Summary` line must match the graph's `added` / `modified` totals.

 Cross-check one against the other and state any disagreement instead of silently preferring a tool; Each of them was blind to something the other saw.

 **Build a change registry, not just an object list — one row per atomic change, not per object.** An object is not the right unit of analysis: a single object routinely carries several independent changes (own attributes, own forms, several interceptors, each doing something unrelated to the others). Track every own attribute / own tabular section / own form / interceptor / exported procedure as its own row (`Объект | Механизм | Куда пишет/что читает | Блок`), leaving `Блок` empty until step 4 fills it in. This is what catches a case like a document that carries both a uniform "auto-create a registry entry" interceptor (block A) *and* its own attributes plus a second, differently-named `&ИзменениеИКонтроль` interceptor whose own insertion does something unrelated (block B) — assigning the whole object to block A on the strength of the first interceptor found would silently drop block B's requirement. **Dump every insert block into a file before grouping: run `1c-insert-blocks` ([docs/insert-blocks.md](docs/insert-blocks.md)) and redirect its output.** This is a safeguard, not an optimisation. A confident «this document is abandoned» was refuted only by an author's comment inside an insert block of a *different* object, found by searching the full dump for something else; reading blocks on demand, per object already classified, would have sent out advice to delete a live object. The tool parses the bare markers (`#Вставка`, not `// #Вставка`), flags blocks with no executable line and blocks inside `&Перед` / `&После` where the markers are inert, and decides what zero means: blocks absent while `&ИзменениеИКонтроль` routines exist is a parse failure (exit code 2), and both absent is an extension of another kind, built from `&Перед` / `&После` / `&Вместо` and own modules. **For an `&ИзменениеИКонтроль` row, fill `Куда пишет/что читает` from its `#Вставка`/`#КонецВставки` blocks only**, not from the whole body — the rest of the body is a verbatim copy of the typical routine. Describing the whole body attributes typical behaviour to the extension: a typical register write in the copied body reads as the extension's change although the base routine already performs it and the insertion may only add, say, a call into a notification mechanism — and step 4's grouping then follows the wrong shared object.

 **Generate the registry from the source tree, not from a search for an already-known pattern name.** A pattern-first search (e.g. `bsl_find_symbol("<the interceptor name you already know>")`) can only ever surface what it already went looking for — it structurally cannot find a sibling object's *differently-named* second interceptor, because nobody had a reason to search for that name. Run **`registry-builder`** ([docs/registry-builder.md](docs/registry-builder.md)) — it walks the extension tree directly (same `ObjectBelonging`/interceptor-scanning logic as `cfe-diff -Mode A`, self-contained per this skill's convention) and emits one row per own attribute/tabular section/interceptor/own-form-routine with `Блок` left empty, so nothing gets into the registry only because someone thought to search for it. Use `-CompareAgainst <already-written-report.md>` to get a coverage check against a draft report — treat its output as "not even mentioned" evidence, not as a strict per-mechanism diff (see the tool's own "Known gaps" for exactly what it does and does not prove). **Scope the check to objects that have own content.** Zero-content adoptions are described in aggregate by design, so a bare-name comparison flags every one of them as missing: That is 81 false positives against 2 genuine omissions, and at that ratio the check gets skipped — which is how the 2 genuine ones survive.

 **Dispatcher decomposition — when one procedure is itself a multi-block dispatcher.** If a single procedure's body contains **more than one** `Если`/`ИначеЕсли` branch comparing against metadata identity or type (`ОбъектМетаданных = Метаданные.X.Y`, `ТипЗнч(...) = Тип(...)`), one registry row for "the procedure" is not enough — one procedure can carry dozens of branches for one functional block and a couple of branches for a completely different one. `registry-builder` flags this automatically (`DISPATCHER` rows, with a branch count) and gives each such row a `Форм: ?` cell: write the number of distinct branch shapes into it. `1` is a legal answer; a `?` left in place fails step 5's gate exactly as an empty `Блок` does. While this was prose, one dispatcher of five got decomposed — not for cost, the analyst judged the rest not worth it; an empty cell cannot be judged away. **Three different numbers live here and only the third is the unit of analysis:** the tool's count of metadata comparisons is an upper bound (it counts commented-out comparisons too); the number of `Если`/`ИначеЕсли` branches is several times smaller, because one branch can hold a couple of dozen comparisons joined by `ИЛИ` — the gap is not merely the commented-out ones); and what you decompose by is the number of distinct shapes those branches reduce to. **The discriminator of a shape is the data path the branch reads, not the form of its code.** Two branches calling the same helper are two shapes when the argument that selects the route differs in kind — whichever position that argument occupies, since the routing one is often not the first (the object's own attribute, the owner of an attached file, a business process's subject, a record set's filter dimension); grouping by how the statement looks collapses them and loses exactly the branch that ties a block's own registers to the dispatcher. Reading it that way can give twice the shapes that grouping by how the statement looks gives. Name the three levels explicitly in the registry — it cannot classify the branches itself, only tell you a routine needs the following treatment: decompose to branch level, but **group by unique shape (same block + same mechanism), not by literal branch count** — a row per distinct combination is enough; do not produce dozens of near-duplicate rows for branches that only differ by which metadata type they name. **The cheapest mechanical signal of a hidden second block is one object whose interceptors sit in two different modules — `registry-builder -GroupByModule` prints them; run it at the start of step 1.** A catalogue carries three print-related interceptors in its manager module (one block) and a write interceptor in its object module feeding an integration service (a different block entirely). The same signal has shown a whole family of documents each carrying three independent mechanisms, not two. One run got that signal on the last possible step, after the report sections were on disk, and had to rewrite them. **Also treat a registry row that groups an unusually large number of branches under one `Блок` value as a signal to double-check for a hidden second block** — a rule stated only as "don't lump a shared dispatcher into one block" is easy to skip silently; a visibly oversized row in the artifact itself is not. This does not catch every possible case (a branch could still hide a further sub-distinction), but it is a large, mechanically-triggerable improvement over object-level or procedure-level granularity, and is a pragmatic stopping point rather than an exhaustive guarantee.
2. **Mechanical re-survey — four commands, and all of them before the first line of code is read.** Each one changes what the unit of analysis *is*, so running it late means redoing the analysis rather than extending it. Three of the four were once run late and each cost a rewrite.

 - **Dump every insertion block — `1c-insert-blocks -ExtensionPath … -ConfigPath … [-Summary]`** ([docs/insert-blocks.md](docs/insert-blocks.md)). This is protection, not convenience: a run that read blocks on demand, object by object as it classified them, was about to report a live object as abandoned, and what refuted it was a comment inside *another* object's insertion block — found only because the whole dump happened to be grepable. The summary also settles by itself what this file used to ask you to check by hand: blocks with no executable lines, markers sitting inside an `&Перед`/`&После` body (the whole body is own there, so the markers are inert), and any `&ИзменениеИКонтроль` carrying no block at all — reporting for each whether the base module even exists, so the highest-severity alarm never has to be raised and then retracted.
 - **Close the registry by set difference — `registry-builder -CloseAgainst <output of cfe-diff -Mode A>`.** It also emits the ready `;;`-joined object list that step 3 feeds to `reference-finder`, which removes the hand-built list and its separator trap entirely. `reference-finder` returns `[OWN CONTENT] — adoption is self-explanatory` on the mere presence of an `Ext/` directory, so until you know which modules are empty, several of its verdicts are worthless. The registry is blind to the same thing — `registry-builder` emits a row per own attribute, interceptor or routine, so a module with none produces nothing — and it is not reported as unclassified either, so the run ends on `0 unclassified file(s)` with objects silently absent from the registry. Objects fall into that hole — among them a manager module commented out in full, `&Вместо` annotations included. **Close it with `registry-builder -CloseAgainst <saved cfe-diff -Mode A output>`** ([docs/registry-builder.md](docs/registry-builder.md)): the set difference both ways, a reason per name (`module is empty`, `module is commented out in full`), and `=== closure: N object(s) with content, M in registry, K unaccounted ===`. A set difference, not a list of symptoms: runs that hunted symptoms got 37 candidates, 31 of them false. Save the whole cfe-diff run to a file first; the tool refuses a truncated one. It also lists the objects whose only change is an extended `Predefined` list with adopted items only — zero-content by the predicate, absent from the registry by design. Both outcomes are findings: an empty module on an abandoned object is the evidence of abandonment, an empty module hosting a subscription handler has to be empty — the handler must belong to the extension, so the module exists only to be referenced — and a third reading is the trace of a deliberate decision: One document carries two empty modules because its form is driven from a common module instead, which the author stated in a comment. Read the author's comments before classing an empty module as a leftover; all three readings occurred on one extension.
 - **Group the registry by object and module — `registry-builder -GroupByModule`.** The cheapest high-yield check here: an object whose interceptors sit in two or more modules is two block candidates, because **the module is the natural boundary of a mechanism in 1C** — writing lives in the object module, printing in the manager module, the interface in the form module, so an author's independent mechanisms necessarily separate by module. That is a structural property of the platform, not a heuristic, and it is why the registry's spine is the pair (object × module) and not the object. Run late, the flag *corrects* a finished grouping: It surfaced a third mechanism on eleven documents after section 2 was already on disk, forcing a new scenario plus edits to the navigation table and every counter. Run here, it prevents that.
 - **Census the dispatchers.** Every `DISPATCHER` row of the registry carries `Форм: ?`. Fill it for each row before reading bodies — `1` is a legitimate answer, blank is not. The field exists because a run decomposed one dispatcher of five and skipped the rest, not from cost (two dispatchers of comparable size cost the same minutes) but from judging the marginal value low; an empty cell in an artifact cannot be decided away, while prose asking for the same thing can.

 **The semantic checkers belong here too — a mechanical supplement, never a substitute for reading.** A full line-by-line reading pass does not scale to hundreds of objects, and a `grep`-scale pass over the same tree misses semantic defects that still parse as valid BSL. Run the narrow checkers as a mechanical supplement. **Three of them take the tree; the fourth does not** — `1c-defined-type-dispatch-checker` declares `-DefinedType` and `-BslFile` as required, so it runs once per suspected dispatch routine and cannot be pointed at the extension as a whole. Budget for that: the routines worth checking come from step 1's `DISPATCHER` rows, not from a single sweep.

 - `1c-enum-value-checker` — enum-value literals referencing a value the enum does not have.
 - `1c-defined-type-dispatch-checker` — per suspected dispatch routine, a `DefinedType` member not handled by any branch.
 - `1c-broken-metadata-path-checker` — hardcoded `"Тип.Имя.Форма..."` literals referencing an object that does not exist.
 - `1c-dead-code-after-insert-checker` — a top-level unconditional `Возврат` shadowing typical code or the extension's own code that follows it. **Only top-level:** a second `Возврат` nested inside an `Если` — including inside an insertion block — is not found by it and stays with reading. **On an extension built out of `#Вставка` its usual hit is intent, not a defect**, so classify each one by where the `Возврат` sits: at the end of an insertion block it is a deliberate replacement of the typical branch and belongs in section 2 as a scenario, while a `Возврат` outside any insertion, or before one, is the defect the checker is named for. Most hits are deliberate replacements; filing them as defects moves real scenarios out of the report.

 **One more check, cheap and not covered by any of the four: an `&ИзменениеИКонтроль` that contains no `#Вставка` block at all.** The routine is then a verbatim copy of the base body with nothing added, which would mean the extension silently froze a copy of typical logic — the highest-severity finding this workflow can produce. **State it as one compound condition rather than an alarm followed by a retraction: no `#Вставка` **and** the base module file exists **and** it declares the intercepted routine.** Testing for the base file costs one check on the same relative path, while raising the alarm costs a pass over every interceptor — so evaluate the cheap clause first and the intermediate panic never arises.** The single hit turned out to have no base module file whatsoever, so there was nothing to freeze and the alarm was false. Reported without that second step, this check manufactures maximum-severity false positives.

 Every finding is still a candidate, not an automatic report entry — confirm each one against the actual source before writing it into section 2 or 4, same as any other finding in this workflow.

3. **Explain zero-content adoptions.** "Zero-content" needs a predicate, not a phrase — three runs built it three different ways before it was stable, because two cases sit on the boundary. **It lives in code, once:** `registry-builder -CloseAgainst` applies it to every object of the saved `cfe-diff -Mode A` output and prints the zero-content borrowed objects as one `;;`-joined line, ready for the reference finder. The table is in [docs/registry-builder.md](docs/registry-builder.md) → «Own-content predicate»; do not keep a second copy of it. The two boundary cases: a module that exists but declares no interceptor **has** content (it is own code; its emptiness is the closure's question), and an extended `Predefined` with adopted items only **has none** — say so explicitly in the report.

 For every object the predicate calls zero-content, run the **reference finder** ([docs/reference-finder.md](docs/reference-finder.md)) to find the technical reason it was adopted (composite-type reference, a reference from the extension's metadata — subsystem content, role rights, command interface — or a code/query reference) or confirm it has none (candidate for exclusion). **Layouts are where a picture or a style item is referenced, so check them — and in an XML dump that check is free.** Look first at what the dump actually holds: `find <ext> -name Template.xml` against `find <ext> -iname '*.mxl'`. A spreadsheet layout exported to XML opens with `<document xmlns="http://v8.1c.ru/8.2/data/spreadsheet">` and is fully searchable, so scan all of them for `БиблиотекаКартинок.<Имя>` and `style:<Имя>` and settle the question: where every layout is XML, one command closes it. **Only a binary `.mxl` is the blind spot**, and only then is the honest wording "candidate — open those layouts in the Designer first" instead of "candidate". **The tool's own verdicts are typed and trustworthy — it matches `cfg:DefinedType.X`, `<v8:Type>`, `CatalogRef.X`, not bare names. The trap is in the manual search you run beside it.** A hit is only a reference when it names the object itself, and searching for a bare object name also matches every longer name containing it, and a compound 1C name makes that routine: A search for a chart-of-calculation-types name matched an information register and a defined type whose own names merely end in it, and the run wrote both into the report as evidence that the adoption was required — it was not. Read the matched line: a real reference is a typed token (`ChartOfCalculationTypesRef.<Имя>`, `<v8:Type>`, a manager call), not the object's name occurring inside another identifier. This cuts both ways — the cost of a false reference is an object kept forever, the cost of a missed one is advice to delete something load-bearing.

 **Two mechanics of this tool that silently mislead.** The batch separator is `;;` — a single `;` does not error, it merges the whole list into one name, returns one `[?]` verdict and exits 0, which reads as "the tool died on the first object". On speed: measured at roughly 0.6 s per object, so a whole-extension batch belongs in the foreground. **Building the `;;` list is where it actually goes wrong:** `paste -sd';;'` cycles through the delimiter's characters and therefore emits a single `;`, which is exactly the input that merges the list into one name. Join in a language that takes the separator literally — `python3 -c "import sys; print(';;'.join(l.strip() for l in sys.stdin if l.strip()))"`. The tool takes `-ExtensionPath` and `-Object`; it declares no `-ConfigPath`.

 **Two verdicts of this tool that are not answers.** `Unknown or unsupported object type` — it has no map for `Language` or `DocumentJournal` among others (a couple of objects per extension), and that object simply has no verdict yet. **Resolve those by hand immediately rather than parking them** — there are only a couple per extension and each costs one search; Both unsupported objects turned out to have a plain reference (a language named as `<DefaultLanguage>` and inside every MXL template; a document journal used as a query table in a web service). Parked, they drift into the removal-candidate list by default, which is the one list where a silent default is expensive. And **`[OWN CONTENT] — adoption is self-explanatory` fires on the presence of an `Ext/` directory, without opening the module**: modules of 3 bytes — a BOM and nothing else — do occur, and objects get that verdict on one. Check the file's size before accepting it. An empty module is itself a finding with two very different readings: for an abandoned object it is evidence of exactly that, while for a subscription handler's host module the emptiness is required — the handler has to belong to the extension, so the module exists to be extended and carries nothing of its own.
4. **Read the bodies** — every insertion block, every own module, every form of an adopted object against its snapshot (see «Forms»). **Walk the (object × module) grid from step 2 top to bottom, not the blocks you already suspect.** A run that organised its reading around its own hypothesised blocks nearly reported a live object as abandoned and found a whole third mechanism last instead of first: reading by hypothesis saves reading and narrows what can be found by exactly as much.

 **Confirming a uniform pattern is a requirement of this step, not a step of its own.** Treated as a separate phase it creates the illusion that the inventory of mechanisms is known once it is done — it only confirms homogeneity inside whatever you already thought to look for, and structurally cannot find a second mechanism on the same objects; that is what the grid walk and `-GroupByModule` are for. When several objects look like they implement the same customization independently, search for a shared signature (a region name, a distinctive procedure name) across all `ManagerModule.bsl`/`ObjectModule.bsl` files to confirm the pattern is genuinely uniform and to catch any object that implements it but would otherwise be mis-grouped in step 4. If `onec-hbk-bsl-*` (or an equivalent BSL symbol-index MCP — `1c-code-metadata-mcp`'s `compact_symbol(name=...)` is equivalent for this) is exposed, prefer `bsl_find_symbol(name=..., limit=<enough to cover every hit>)` / `compact_symbol` over `Grep` for this — it returns every definition of a same-named procedure across the whole workspace with exact `file_path`/`line` in one structured call, instead of a text match you still have to de-duplicate by hand. **Either way, a matching interceptor/procedure name is a starting point, not a conclusion** — read the actual body of every matched object before asserting they all share the implementation. One of many siblings sharing an interceptor name can call a completely different — even broken — mechanism, and a conclusion drawn from the name alone is then contradicted by that unread body. Enumerating candidates is not the same as confirming they are the same pattern — only reading each body does that.
5. **Group into functional blocks** — objects that are `[OWN]` (fully new) or `[BORROWED]` with real own content rarely stand alone; group them by the business scenario they implement (e.g. "outgoing document registry", "personal-cabinet integration", "RIB exchange"). This step is currently manual — read the code and follow cross-references. Where `1c-graph-metadata-mcp` is exposed, route each question through the table in "MCP usage" below (call arguments — `content/skills/1c-impact/SKILL.md`); `onec-hbk-bsl-*`'s `bsl_callers`/`bsl_callees` remain an alternative for call tracing where that server is exposed. **A register reached by two or more objects' code is a grouping candidate, not a conclusion** — check whether each access sits inside a `#Вставка` block (see the registry rule in step 1) before treating the shared register as the extension's link between those objects. Forms of the extension — `1c-form-basediff` for every form of an adopted object, which is not optional: see «Forms» under "MCP usage" for what a form has to yield and why reading one without its base counterpart misattributes typical behaviour.

 **Before reading code from scratch, check [docs/metadata-modification-patterns.md](docs/metadata-modification-patterns.md)** — a reference of the recurring reasons each metadata type tends to get touched (e.g. an `InformationRegister` gaining a dimension-gap shadow copy, an `ExchangePlan` getting scoped/filtered replication, a `DefinedType` growing to cover a new own object). It speeds up recognizing *why* an object was likely adopted/changed — it does not replace reading the object's actual code before writing the reason into the report.

 **For every wholly-new `Report`/`DataProcessor` with an SKD-only schema (no `ObjectModule`/`ManagerModule` code), read its DCS query — or run `dcs-query-fields-extractor` once per object (`-Object` is required; it does not take a tree)** ([docs/dcs-query-fields-extractor.md](docs/dcs-query-fields-extractor.md)) **— *before* assigning it to a functional block.** A shared name suffix says nothing about what a report does — its query may read data unrelated to the objects it is named like. Group by what the query actually reads, not by name similarity with other objects in the extension.

 **Exchange-plan / RIB participation is a requirement of the owning block, not a separate infrastructure block.** When an object already belongs to a functional block by its own business purpose, and that same object also participates in an exchange plan — listed in `Ext/Content.xml`, or registered/filtered by code (a registration-rules handler, a hardcoded dispatcher, a registration-settings helper) — describe that participation as part of *that block's* requirements. Do not carve out a standalone "exchange mechanism" / "RIB filter" node to hold it, even when the registration code is physically shared across several blocks (one dispatcher, one common registration-settings module). A shared module or dispatcher does not make a shared requirement: each block's objects usually have their own describable registration path — a dedicated insertion into the typical registration-settings channel, or their own branches in a shared fallback dispatcher, which stay attributable to the block they serve. Splitting a shared mechanism's description across the blocks it actually serves — instead of centralizing it in an artificial node — keeps every requirement traceable to the business need that created it, and lets each block's update risk be assessed on its own evidence instead of one blended risk statement. The **only** thing that legitimately stays a cross-cutting note instead of living inside a block is the shared mechanism's own recurring-maintenance risk, and only when there is concrete evidence for it (e.g. version-marker comments proving the mechanism has already been revised more than once) — record that in the report's risk section (see skeleton §7 below), not as its own functional-block subsection.
6. **Completeness sweep and the closure gates** — cross-check every object that has *any* `Ext` subfolder (real code/forms/templates) against what step 3 already classified. **Every form carrying own content is decomposed, not just named:** its events with their annotation kind, its element→data bindings and its commands, and — for a form of an adopted object — the same reading of the base configuration's form beside it. A report that lists a form's routine names without its bindings has not analysed that form, and saying so in the limitations does not make the sweep complete; `1c-form-info` renders one form in a few dozen lines, so cost is not a reason to skip it. **Take the form count from `cfe-diff -Mode A`:** The true count is 21 and a `*/Forms/*` glob returns 20, missing the common form — the same trap the enumeration paragraph below describes, and the reason no total is quoted here as a target. For a one-call inventory per metadata type use the graph's `search_metadata {"operation": "list_extension_objects"}` from step 1 — not `bsl_meta_collection`, which needs the `onec-hbk-bsl-*` pair that most deployments do not ship. Do not declare the analysis complete on the strength of "the customer described N reasons" alone — enumerate every object with real content and make sure each one lands in a named block, a "confirmed no effect" note, or an explicit open question. This is the step that most often finds forgotten reports, disabled data processors, and orphaned print templates.

 **The closure gate is the change registry's `Блок` column, not the object list.** "Every object landed somewhere" is not sufficient — walk every row of step 1's change registry and confirm `Блок` is filled (or explicitly marked unassigned, per report skeleton §7 below), and every `DISPATCHER` row's `Форм` holds a number, before the analysis counts as complete. An object with all-but-one of its rows assigned is not "done" — the one empty row is exactly the kind of thing this gate exists to catch.

 **The second gate is `Форм:` on every `DISPATCHER` row** (step 2) — same mechanism as `Блок` and the same reason: a blank cell is visible and cannot be decided away, whereas prose asking for the same decomposition can be skipped silently.

 **The third gate is the scenario record, and it is the one that fails silently.** Before writing conclusions, walk section 2 and confirm that every scenario carries its id, its GIVEN/WHEN/THEN, a re-runnable locator per evidence bullet (`файл:строка` for BSL, `файл` + element/attribute for XML), and its own `Поведение:` / `Назначение:` pair. Measured over three independent runs of this skill on one extension: the registry gate held every time (100% of rows assigned), while the scenario record decayed from a full record with per-scenario grading to **zero ids, no GIVEN/WHEN/THEN and grading at block level** — in runs whose prose was otherwise strong. A block graded once is not the same claim as its scenarios graded individually: block-level grading quietly promotes the best-evidenced scenario's confidence onto every other scenario under that heading. What no gate checks is what goes first, so check this explicitly rather than trusting that the methodology was read.



 **Two general brakes, both of which stopped a false class of defects And neither of which any checker implements.**

 - **A metadata token names an object that is not in the extension — that is normally fine.** For `Метаданные.<Коллекция>.<Имя>` (and the same shape in a dispatcher branch), the test is which tree the object lives in: absent from the extension *and* from the base configuration — a defect; present in the base but not adopted — normal and needs no action, because a dispatcher may legitimately reason about objects it never touches. Without that distinction the suspicion "it names objects the extension does not contain" hangs unresolved; with it, one script over every token answers it, and the same script becomes the post-update regression check for the risk section.
 - **An implausibly large count of same-shaped defects is evidence about your enumeration, not about the code.** A production system does not carry two dozen calls that fail on every execution. Before writing a defect class whose count is more than a few, re-derive how you enumerated it: A run was about to report two dozen broken references to predefined items, having looked for `<Predefined>` inside each object's XML — the predefined items live in a separate `<Объект>/Ext/Predefined.xml`, and every one of them resolved. Treat a big round number of identical findings as a prompt to re-check the method first.
7. **Write the report** using the section skeleton below.

## Report skeleton

A finished analysis is a single Markdown file with these sections, **in this order, which does not change** — a reader who is told the shape can navigate it. Section 2 grows to well over a thousand lines on a mid-sized extension, and the answer to that is **not** reordering: put a short navigation table in section 1 (scenario id → block → one line) and leave sections 2 and 3 where they belong.


| # | Section | Content |
|---|---|---|
| 0 | Исходные данные от заказчика | Verbatim customer input, numbered as given |
| 1 | Общие сведения о расширении + Метод анализа | Configuration/extension identity, platform version, and an explicit methodology note (what "adopted" vs "own" means, per-child `ObjectBelonging`, not just open `ChildObjects`) |
| 2 | Изменённые сценарии и причины модификации | **Scenarios are the spine here, the mechanics are their evidence.** Every scenario is written as the same record, and the record is not optional prose: **a stable id** (`SC-01`, cited from the summary table and the registry), **штатно** — what the stock configuration does, **с расширением** — what the extension makes it, **вид** (see the kinds in `docs/methodology.md`), **GIVEN / WHEN / THEN**, **доказательства** each with a locator another person can re-run — `файл:строка` for BSL, and `файл` plus the element or attribute for XML (`Form.xml` → `InputField name="X"`, `Content.xml` → the `<Metadata>` entry), since an XML line number locates nothing a reader can check and shifts on the next dump — each marked `прямое`/`косвенное` per the strength table, **что сломается при снятии**, and **both grades, each as its own bullet in exactly this literal form — `- **Поведение:** <оценка>` and `- **Назначение:** <оценка>`, the verdict being the whole rest of the line and any explanation on the next line, one pair per scenario and never one per block**. The literal form is the point: the gate is then two `grep -c` anchored at the end of the line, whereas free-form grading defeats even a purpose-written checker — Three records hid the verdict inside a bold label and one buried "подтверждено кодом" in the prose of a `вероятно` line, and the run's own script mis-scored all four. "First token" is not enough either: verdicts have been continued with prose after a semicolon and with a parenthetical citation, and a run's own checker — splitting on the first punctuation — reported full compliance over a file where most lines did not conform. Write the text to fit a `grep -vx` of the four permitted verdicts, not a regex to fit the text. **The `Назначение` grade is decided against this scenario's own evidence, not against which requirement the block sits under.** That the customer named the object, or that the block answers their point N, is not confirmation of *this* purpose: compare what they said the thing is for with what the code here actually does. Where the two differ, the grade is `противоречит словам заказчика` and both formulations are quoted side by side — measured failure mode: a run described an integration object's operations correctly, established that none of them touches the data the customer said that integration exists to exchange, and still graded it `подтверждено заказчиком` — because the customer's own wording had named that object. The prose was right and the grade was wrong, which is the hard case: nothing in the scenario looks careless. An empty `противоречит` column is a finding only once you have checked for it. **A defect is not a scenario, and it takes a different literal rather than a fifth grade.** Keep it physically inside the `2.x` subsection where it belongs — a broken twelfth implementation of an interceptor that eleven siblings implement correctly means something only *next to* the claim that the mechanism is uniform, and exiling it to its own section destroys that adjacency. Grade it as `- **Дефект:** подтверждён кодом` or `- **Дефект:** требует проверки на ИБ`, counted separately, so it neither dilutes the `Назначение` scale nor weakens the gate. A run that instead invented a fifth value (`не применимо`) for four defect records did both. `docs/methodology.md → Scenarios are the spine` holds the kinds, the strength table and the mapping onto `openspec/specs/`; it does not replace this record. One numbered subsection per functional block found in step 4; dedicate a subsection to any single object worth a deep dive; flag obsolete/candidate-for-removal findings explicitly in the subsection title. If a block's own objects participate in an exchange plan (RIB or otherwise), describe that as a named part of *this* subsection (e.g. an "exchange mechanism" paragraph) — do not create a separate cross-block subsection for it (see step 3's exchange-plan rule) |
| 3 | Сводная таблица изменённых объектов | One row group per object type, cross-referencing the relevant `2.x` subsection |
| 4 | Не подтверждено / требует уточнения у автора расширения | Every object adopted with zero real content, with its reference-finder verdict; use blockquotes to record items that started here and were later closed |
| 5 | Вопросы к заказчику для следующего раунда обсуждения | Only genuinely open questions — a question closed by evidence found later in the same session must be moved into a blockquote here (or into the relevant `2.x`/`4` section) and removed from the numbered list; renumber after every removal |
| 6 | Итоговый вывод | The functional blocks restated as a short list, isolated additions, confirmed-obsolete items, corrections to earlier (wrong) claims |
| 7 | Риски и опасения заказчика при обновлении типовой конфигурации | Only genuine update-time risks, tied to specific objects/mechanisms found in section 2 |

Keep sections 4 and 5 honest: an item stays in "open questions" only while it is genuinely unresolved. As soon as code/reference evidence closes it, move the resolution into the relevant numbered section and strike it from section 5 — do not leave a question in section 5 that the analysis itself has already answered.

**Appendix — change registry.** Include step 1's change registry (`Объект | Механизм | Куда пишет/что читает | Блок`) as a report appendix, not just scratch working material — it is the evidence trail that shows every atomic change was actually accounted for, and lets a reader audit section 2's block assignments against the underlying granular facts instead of taking them on faith. Keep rows collapsed by unique shape (per step 1's dispatcher-decomposition rule) — the appendix should stay a few dozen rows for a mid-sized extension, not hundreds.

**Collapsing rows for the appendix is a write-up step that can silently undo everything step 1 just fixed — verify before collapsing, don't collapse on appearance.** Objects that look alike (same type, same primary interceptor) can still differ by a second own interceptor or own attributes, and one shared appendix line drops those rows although the raw registry has them. The tool being right does not make the write-up right — before folding several objects' rows into one appendix line, re-open each object's *own* full row set (not just its first/primary row) and confirm every single row is actually covered by the shared explanation. One row that doesn't fit means that object gets its own line, never a share of the group's.

**Adopted-object staleness — read before trusting a "declared value" / "composition" result from `1c-enum-value-checker` or `1c-defined-type-dispatch-checker`.** An extension's own copy of an `Adopted` (typical) object can be a stale snapshot with far fewer children than the base configuration currently declares. Both tools resolve this by preferring the base configuration's copy over the extension's own snapshot whenever `-ConfigPath` is given and the object is `Adopted` — **always pass `-ConfigPath`** — to `1c-enum-value-checker`, `1c-defined-type-dispatch-checker` **and `1c-broken-metadata-path-checker`**, which declares it "optional but recommended": without it an object that exists only in the base configuration is reported `UNKNOWN` instead of a confirmed verdict, so a genuinely broken path hides among the unknowns — measured `0 broken, 2 unknown` without the argument against `1 broken` with it. Running without it is running without it is a degraded, unverified mode.

## Preconditions — both source trees, and a shell

**An XML dump of the extension *and* of the base configuration.** The skill describes how to degrade without a shell; it cannot degrade without the base tree. Measured Five classes of finding need `src`, and one of them is impossible without it: the extension's own snapshot of an adopted `DefinedType` can declare **zero** types, so its real composition is only in the base — which is what a dispatch-completeness check rests on. The others: whether a subscription handler named by the extension exists at all; classifying each exchange-plan entry the extension adds as a typical object or its own; deciding whether a hardcoded metadata path is broken or merely base-only (without `-ConfigPath` a real defect hides among the `unknown`s); and the brake "the object is in the base but not adopted — that is normal". An extension delivered only as a `.cfe`, or a base configuration available only inside an infobase, turns those five into unknowns. Say so in section 1 rather than reporting the weaker conclusions as full ones.

**An extension of a different nature changes which rules apply.** The insertion-block machinery — the `#Вставка` scoping rule, `1c-insert-blocks`, the intent-vs-defect axis of `1c-dead-code-after-insert-checker`, dispatcher decomposition — all presuppose `&ИзменениеИКонтроль`. On an extension built from `&Перед`/`&После` in its own modules, zero insertion blocks is the truth and not a tooling failure, and every unconditional `Возврат` has to be judged by hand. Exchange-plan rules and `1c-exchangeplan-content` simply do not apply without an exchange plan. The inventory, the reference search, the form diff and the closure gates hold regardless.

## Environment constraints — tool availability is not guaranteed

Both `cfe-diff` and `1c-reference-finder` are Python scripts that need a shell to run. **A subagent invocation can end up with only `Read`/`Write`/`Edit`/`Grep`/`Glob` available, with no working shell and no MCP tools, even when the invoking agent's own configuration lists `Bash`/`MCP` among its tools.** Check for a working shell at the very start of a run (attempt a trivial command) rather than assuming it and discovering the failure mid-workflow. If no shell is available:

- Do the per-child `ObjectBelonging` check from step 1 by direct `Read`/`Grep` of the metadata XML (same logic `cfe-diff -Mode A` implements — see `content/skills/1c-metadata-manage/tools/1c-cfe-manage/scripts/cfe-diff.py` for the exact algorithm if in doubt).
- Do the reference search from step 2 by `Grep` for the object's Ref-type token and manager/query-style Cyrillic name across the extension tree (same logic `reference-finder.py` implements — see [docs/reference-finder.md](docs/reference-finder.md)).
- State plainly in the report's methodology section (section 1) that the check was performed manually because no shell tool was available, not because of a missing Python dependency — these are different failure modes and the report should not conflate them.

## MCP usage

This is analysis work, not a BSL/metadata edit — the BSL validation gates of `content/rules/verification-gates.md` (`syntaxcheck`/`check_1c_code`/`review_1c_code`) do not apply. Use the project's search/graph MCP tools (`content/skills/mcp-1c-tools/SKILL.md`, `content/rules/mcp-first-search.md`) for step 4 (grouping into functional blocks) and to verify claims about base-configuration behavior before writing them into the report, per `content/rules/sdd-integrations.md`'s evidence discipline — every metadata name, attribute, or platform behavior asserted in the report should be grounded in a source you actually checked, not assumed from a similar-looking object.

### BSL static-analysis MCP (`onec-hbk-bsl-*`) — usually absent

Some deployments expose a BSL language-server pair (`onec-hbk-bsl-main` over the base config, `onec-hbk-bsl-ext` over the extension). Check `.mcp.json`; most deployments of this skill do not ship it, and nothing in this workflow depends on it. Where it exists, `bsl_find_symbol` enumerates same-named routines for the pattern step and `bsl_meta_collection` inventories a metadata collection. Never substitute its `bsl_meta_object` for the `ObjectBelonging` check — it reports an object's structure with no adoption flag, which reintroduces the exact mistake this skill exists to prevent.

### `1c-code-metadata-mcp` — limits for this workflow; prefer the offline `1c-form-info`

Not part of every deployment — check `.mcp.json`; tool catalogue: `content/skills/mcp-1c-tools/docs/1c-code-metadata-mcp.md`. It indexes the base configuration together with the discovered extensions, but its artifact tools answer from the base layer only:

- **Does not answer `ObjectBelonging`.** `get_metadata_details(...)` returns an object's attribute list without an adoption flag, whatever the scope or `origin`, and without the attributes the extension added. `cfe-diff -Mode A` / the per-child `ObjectBelonging` check remain the only authoritative source for "did the extension add this".
- **Artifact tools do not see what the extension added.** `get_report_artifact` does not find a report the extension added, and `get_role_artifact` does not list rights declared in the extension's adopted roles. For rights use the graph server's `get_access_rights`; for the extension's reports `get_report_dcs_lineage` does not help either (base reports only) — use `dcs-query-fields-extractor` or read the report's `Template.xml`.
- **`compact_symbol(name=...)` serves step 3** — it returns every same-named definition across base and extension with an exact line range; a substitute for `bsl_find_symbol` where `onec-hbk-bsl-*` is not exposed.
- **Form layout — the offline `1c-form-info` tool** (`content/skills/1c-metadata-manage/tools/1c-form-info/scripts/form-info.py`, documented in `content/skills/1c-metadata-manage/docs/form-manage.md`), not `inspect_form_layout`: it renders the element hierarchy with each handler attached to its element, typed attributes, and form commands/parameters.

Net effect: do not route steps 1–3 through this server. `compact_symbol` is the one call worth using (step 3). A deployment that does not ship it loses nothing this workflow depends on.

### `1c-graph-metadata-mcp` — what extension analysis adds to `1c-impact`

The server is not part of every deployment — check `.mcp.json`. Calls and arguments are not repeated here: usages, call chains, register writers, `compare_base_and_extension` and `resolve_effective_entity` — `content/skills/1c-impact/SKILL.md`; forms — `content/skills/1c-form-inspect/SKILL.md`; rights, event subscriptions, DCS lineage, data links and the base/extension layer contract — `content/skills/mcp-1c-tools/docs/1c-graph-metadata-mcp.md`. This section maps the workflow's questions to those tools and adds what matters for an extension.

| Enum values | `search_metadata` with `{"operation": "list_enum_values", "object_name": "<Имя>"}` | Not `find_predefined_values` — it reads predefined items only and answers empty for an enum |
| Bindings and handlers of the extension's forms | offline `1c-form-info` — primary; `find_form_links` / `get_form_structure` as the cross-check | See «Forms» below |
| Inventory of the whole extension | `cfe-diff -Mode A` | Not `compare_graph_scope(extension_ref=<layer>)`: it gives layer-level totals — a diff of graph entities with an `add`/`change`/`delete` summary, paged by cursor — not the per-object own-vs-borrowed inventory step 1 needs |
| What breaks if an adoption is dropped (step 5) | `trace_impact(object_name, direction="downstream", depth=2)` | Walks `USED_IN` / `DO_MOVEMENTS_IN` / `CALLS` by level and names the intermediate of each indirect hit in `via`, lists the object's forms, and states that extension layers were taken into account. Verified against the XML on a three-link chain: a catalogue the extension added → the typical catalogue that carries its type → the document reached `via` that catalogue, which references it nowhere directly |
| Which layer a name means, before any path call | `resolve_graph_entity(reference="Документ.<Имя>")` | For an adopted object it answers `ambiguous` with both candidates, each carrying `origin: base` / `origin: extension`, `layer_name` and its `node_id`. That is also the cheapest check of whether the extension touches the object at all, and the source of the `node_id` the path tools need |
| Exchange-plan composition | `1c-exchangeplan-content` | No MCP tool parses `Ext/Content.xml` |

**There is no Cypher escape hatch through this server** (re-verified 2026-09-30). Routine nodes do carry `extension_mode` / `extension_target` properties in the database (measured 2026-09-29: 99 of the 383 routines of one extension layer), but no MCP tool surfaces either property in its response, and `run_graph_cypher_template` executes an allowlist of nine named templates (`objects_by_name`, `object_modules`, `object_forms`, `object_attributes`, `object_attribute_properties`, `object_tabular_parts`, `object_neighbours`, `object_counts_by_category`, `objects_in_category`) — not arbitrary Cypher. So advice to "just query the graph" for an annotation inventory is not executable from this workflow at all; only a direct database connection reaches those properties, and the next paragraph is why that would not settle the question either. The annotation list stays with `cfe-diff -Mode A` plus a direct read of every common form's module.

**Two graph tools that look made for this workflow and are not.** Both were measured on this extension on 2026-09-29; use them only as described.

- **`get_object_dossier` merges the layers into one list.** On an adopted document it returned 25 attributes — the base's 15 plus the extension's 10 — with the 8 adopted ones listed twice under the same name, and the extension's two own attributes nowhere marked as own. `project_name="<layer>"` changes only the heading, not the list. So the dossier is a fine passport of a *base* object, and never evidence of what the extension added: that stays with `compare_base_and_extension` and `cfe-diff -Mode A`.
- **`find_graph_path` needs an `edge_types` allowlist.** Asked how the extension's report relates to the document its queries read, it returned instead a path through a role: report ←`GRANTS_ACCESS_TO`— `Роль.ПолныеПрава` (extension) —`EXTENDS`→ the base role —`GRANTS_ACCESS_TO`→ the document. Formally true, analytically worthless: a full-rights role touches everything. The real link was not found at all — the walk skips nodes without a declared identity (`Layout`, `Command`, `EventSubscription`, per its own `warnings`), so a report → schema → data set → table chain is invisible to it, and it stopped on `max_nodes` with `exhaustive: false`. Pass `edge_types` (e.g. `["CALLS", "USED_IN"]`), read `data.exhaustive` and `data.explored.stop_reason` before believing either a hit or a miss, and take a report's data links from `get_report_dcs_lineage` instead.

**Attributing a hit to the extension.** With the base and the extension as layers of one project, `trace_call_chain`, `find_object_referrers` and `get_access_rights` answer across both layers. A hit belongs to the extension only when its file lies in the extension dump — and, inside an `&ИзменениеИКонтроль` routine, only within a `#Вставка` block. An adopted object or role exists in both layers, so a call naming it can answer `ambiguous` with a `candidates` list: pass the chosen candidate's `node_id` as `object_name` (or `role`) — `find_object_referrers` and `get_access_rights` accept it. General rule for ambiguous entities — `content/skills/mcp-1c-tools/docs/1c-graph-metadata-mcp.md → Contract and scope`.

**`compare_base_and_extension(object_name, extension_name)`** lists, per object, the attributes, forms and routines taken from the base, overridden or added by the extension; a routine appears in one of these groups only. `extension_name` is the layer name — the `Name` in the extension's own `Configuration.xml`, not the directory it was dumped into; a directory name finds nothing. It compares the layers as two node sets by name, independently of `cfe-diff -Mode A`'s XML reading — cross-check the two. `search_metadata({"operation": "list_extension_objects", "extension_name":..., "extends_type": "added"})` lists the extension's new top-level objects separately from the adopted ones. The comparison covers attributes, forms and routines only: roles, RLS, subsystem composition and command-interface changes are outside it, and an empty "Формы" section for one object says nothing about form overrides elsewhere — step 5's completeness sweep stays mandatory.

**Forms.** The primary tool is the offline `1c-form-info` (`content/skills/1c-metadata-manage/tools/1c-form-info/scripts/form-info.py`). It belongs to another skill, and running it here is explicitly allowed: it only reads a `Form.xml` and prints, so it breaks no rule of this analysis-only skill. It renders the element tree with each element's data binding, the form's events with their extension annotation kind (`OnCreateAtServer[After] -> ИК_ПриСозданииНаСервереПосле`), per-element handlers, and marks the file `[EXTENSION]` with its support status.

**Read a form of an adopted object only next to its own `<BaseForm>` snapshot, and let the tool compare the two.**

1. **Run `1c-form-basediff`** ([docs/form-basediff.md](docs/form-basediff.md)) — `-Summary` for the verdicts, then the full output per `markup-changed` form. It compares the live form with the snapshot inside the same `Form.xml` as trees, property by property. It lists lost properties first, each with a control-element check, and reports handler bindings apart from markup. A form whose module alone changed stays `markup-unchanged`. Never compare sets of element names instead: a property removed from an existing element is invisible to that by construction, which is how a removed `ReadOnly` was missed. The base configuration's file is a third point answering a different question, and comparing the snapshot with it yields mostly serialisation artefacts.
2. **Never conclude "no own content", and never propose removing an object, from a name-level comparison.** The cost is asymmetric: missing a change is a gap, declaring an adopted object a removal candidate is advice to delete it. An exchange-plan node form was twice called an empty copy and a removal candidate, while its one edit — a removed read-only flag on two fields — is the only manual way out of a packet-number desynchronisation.

`1c-form-info` (the offline renderer, `content/skills/1c-metadata-manage/docs/form-manage.md`) is optional and secondary: it reads a `Form.xml` and prints the element tree with bindings, handlers and annotation kinds, which helps when a hunk is unclear. It prints only a chosen subset of properties — `Representation`, `HeightInTableRows`, `VerticalStretch` and `AutoMaxHeight` are not in its source at all — so **its silence is never evidence** and a diff of two renderings drops that whole class of edit. Run it with `-Expand '*'`; the default output collapses containers into a table of contents.

The misattribution runs the other way too, so keep the base side in view: on that same form `ФормаЗаписатьИЗакрыть` and `ФормаЗаписать` show `[visible:false]` in the extension's copy, which reads as "the extension hid the write buttons" — and both flags are already in the base form.

**Enumerating the forms is itself a place to lose them.** A form usually lives at `<Object>/Forms/<Name>/Ext/Form.xml`, but a common form *is* the object: its file sits at `CommonForms/<Name>/Ext/Form.xml`, so a sweep matching `*/Forms/*` silently skips it. That is one of the six forms of adopted objects — and the one carrying a changed `Representation`. Take the form list from `cfe-diff -Mode A` or `1c-form-basediff` (which walks every `Ext/Form.xml`) rather than from a path glob, and never pipe that tool into `head`: it dies on SIGPIPE and returns a short answer that looks complete (a fraction of what it prints, losing forms without a word). **The same applies to `1c-exchangeplan-content`, where it costs more:** its answer to the only question worth asking — the diff section, headed `--- Diff: <ИмяПлана> ---`, so a literal search for `--- Diff ---` finds nothing and the tool looks like it answered empty; read it with `sed -n '/--- Diff/,$p'` — is at the very end, so piping it through `head` drops that section entirely while looking like a complete run. Redirect to a file and read the file.

Handlers can also be bound in the XML rather than in the module: on one adopted form every handler — several element `OnChange` plus form-level events — is declared in `Form.xml` with no `&Перед`/`&После` annotation anywhere in the module. A module-only sweep sees none of them.

**Known blind spots, all measured — do not conclude absence from a single tool.** `compare_base_and_extension` answers "no attributes, no forms, no routines" for a common form while that form has an added attribute, command, button and two interceptors. And `<xr:State>Extended</xr:State>` in a form's metadata file says nothing about the markup: it is also present on a form whose module alone changed and whose XML is byte-identical to its snapshot — the markup verdict comes from `1c-form-basediff`, not from the flag. **The graph server misses the common form's module too, so it is not an independent witness there:** it holds **no** routine nodes whose file path lies under `CommonForms/`, which makes every interceptor count derivable from it short by exactly that module's annotations — 41 `&После` against 43 in the sources, while the other three annotation kinds matched the sources exactly. `cfe-diff -Mode A` and `registry-builder` read that module (`Ext/Form/Module.bsl`) from the sources; a count from the graph alone is not. **`compare_base_and_extension`'s own "Переопределены / Добавлены" split is not an interceptor inventory either:** it pairs the layers by routine name, so an interceptor of a platform event lands under "Добавлены" whenever the base module declares no routine of that name — the interceptors bound to platform events. The annotation in the source is authoritative; the graph's column is not.

The graph's `find_form_links` / `get_form_structure` are the cross-check, not the primary source. They answer across layers, so pass a type prefix in `object_name` — `find_form_links(form_name, "Справочник.<Имя>")` — whenever a name may be shared by objects of different categories; form and event nodes carry `category_name` and `config_name`, so the right owner is selectable.
