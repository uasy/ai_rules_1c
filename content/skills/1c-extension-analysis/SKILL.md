# 1C Extension Analysis — Skill Dispatch

Use this skill when the task is **not** to change an extension, but to **understand and document** why it modifies the base configuration — e.g. "analyze this extension and explain why it customizes the typical config", "prepare a report for the customer before a configuration update", "find dead/obsolete adoptions in this extension". For actually *editing* the extension (borrowing, patching, building) use `1c-metadata-manage` (`docs/cfe-manage.md`) instead — this skill is analysis-only and does not write to the extension source tree.

Every configuration and extension is different — this skill and its tools are generic and parametrized (extension path, config path, object name); nothing here is specific to any one customer's standard configuration (ERP, БУХ, УТ, УП, ЗУП, or any other).

**Delegation.** For a full, independent extension audit (the whole workflow below end-to-end, producing the complete report), delegate to the **`1c-extension-analyst`** subagent (`content/agents/extension-analyst.md`, catalog entry in `content/rules/subagents.md`) rather than running the workflow inline — it carries the methodology guardrails (per-child `ObjectBelonging` discipline, completeness-sweep obligation, customer-input-vs-code-fact discipline) that this SKILL.md does not repeat. Run the workflow directly (without delegating) only for a narrow, single-object question (e.g. "why was this one object adopted") where a full report is not the goal.

## Relationship to `1c-metadata-manage` / `cfe-manage`

This skill **builds on top of** `1c-cfe-manage`'s `cfe-diff.py -Mode A`, it does not duplicate it. `cfe-diff -Mode A` already does the single most important and error-prone step correctly: for every object in the extension it classifies `[BORROWED]` vs `[OWN]`, and for borrowed objects it counts **own attrs / own TS / own forms** vs **borrowed items** by descending into `<ChildObjects>` and checking each child's `ObjectBelonging` — not just whether the parent's `<ChildObjects>` tag happens to be open. It also lists every interceptor (`&Перед`/`&После`/`&ИзменениеИКонтроль`/`&Вместо`) per module.

**MCP alternative for a single object.** `1c-graph-metadata-mcp`'s `compare_base_and_extension(object_name=..., extension_name=...)` gives the same per-object structural diff (attributes/forms/routines added, overridden, unchanged) without needing the source dump on disk. It compares the base and extension layers by name instead of parsing XML `ObjectBelonging`, so it fails independently of `cfe-diff -Mode A` — which is what makes it a useful cross-check. The server is not part of every deployment — check `.mcp.json`; setup and extension layers: `content/skills/mcp-1c-tools/docs/1c-graph-metadata-mcp.md`. It is a per-object call, not a whole-extension inventory, so it does not replace step 1 (`cfe-diff -Mode A` for the full object list) — use it to double-check or deep-dive a single object, and fall back to `cfe-diff`/`reference-finder` (offline, file-based, always available) otherwise.

> **Do not re-derive this by hand with ad hoc `grep`/regex on `<ChildObjects>`.** Treating an open (non-self-closed) `<ChildObjects>` as proof of a new attribute/tabular-section/dimension/resource is the classic mistake this skill exists to prevent — an object's child list is open whenever it contains **any** children, even when every single one is itself `ObjectBelonging=Adopted`. Always run `cfe-diff -Mode A` first and read its own/borrowed counts per object; only fall back to manual XML inspection for a single object when `cfe-diff` cannot run (e.g. `lxml` unavailable) or its output is ambiguous.

## Workflow

1. **Inventory** — run `cfe-diff -Mode A` (see `content/skills/1c-metadata-manage/docs/cfe-manage.md`) against the extension and its base configuration source. This gives the full object list, `[BORROWED]`/`[OWN]` split, own-vs-borrowed child counts, and interceptor list in one pass.

   **Build a change registry, not just an object list — one row per atomic change, not per object.** An object is not the right unit of analysis: a single object routinely carries several independent changes (own attributes, own forms, several interceptors, each doing something unrelated to the others). Track every own attribute / own tabular section / own form / interceptor / exported procedure as its own row (`Объект | Механизм | Куда пишет/что читает | Блок`), leaving `Блок` empty until step 3 fills it in. This is what catches a case like a document that carries both a uniform "auto-create a registry entry" interceptor (block A) *and* its own attributes plus a second, differently-named `&ИзменениеИКонтроль` interceptor whose own insertion does something unrelated (block B) — assigning the whole object to block A on the strength of the first interceptor found would silently drop block B's requirement. **For an `&ИзменениеИКонтроль` row, fill `Куда пишет/что читает` from its `#Вставка`/`#КонецВставки` blocks only**, not from the whole body — the rest of the body is a verbatim copy of the typical routine. Describing the whole body attributes typical behaviour to the extension: a typical register write in the copied body reads as the extension's change although the base routine already performs it and the insertion may only add, say, a call into a notification mechanism — and step 3's grouping then follows the wrong shared object.

   **Generate the registry from the source tree, not from a search for an already-known pattern name.** A pattern-first search (e.g. `bsl_find_symbol("<the interceptor name you already know>")`) can only ever surface what it already went looking for — it structurally cannot find a sibling object's *differently-named* second interceptor, because nobody had a reason to search for that name. Run **`registry-builder`** ([docs/registry-builder.md](docs/registry-builder.md)) — it walks the extension tree directly (same `ObjectBelonging`/interceptor-scanning logic as `cfe-diff -Mode A`, self-contained per this skill's convention) and emits one row per own attribute/tabular section/interceptor/own-form-routine with `Блок` left empty, so nothing gets into the registry only because someone thought to search for it. Use `-CompareAgainst <already-written-report.md>` to get a coverage check against a draft report — treat its output as "not even mentioned" evidence, not as a strict per-mechanism diff (see the tool's own "Known gaps" for exactly what it does and does not prove).

   **Dispatcher decomposition — when one procedure is itself a multi-block dispatcher.** If a single procedure's body contains **more than one** `Если`/`ИначеЕсли` branch comparing against metadata identity or type (`ОбъектМетаданных = Метаданные.X.Y`, `ТипЗнч(...) = Тип(...)`), one registry row for "the procedure" is not enough — one procedure can carry dozens of branches for one functional block and a couple of branches for a completely different one. `registry-builder` flags this automatically (`DISPATCHER` rows, with a branch count) — it cannot classify the branches itself, only tell you a routine needs the following treatment: decompose to branch level, but **group by unique shape (same block + same mechanism), not by literal branch count** — a row per distinct combination is enough; do not produce dozens of near-duplicate rows for branches that only differ by which metadata type they name. **Treat a registry row that groups an unusually large number of branches under one `Блок` value as a signal to double-check for a hidden second block** — a rule stated only as "don't lump a shared dispatcher into one block" is easy to skip silently; a visibly oversized row in the artifact itself is not. This does not catch every possible case (a branch could still hide a further sub-distinction), but it is a large, mechanically-triggerable improvement over object-level or procedure-level granularity, and is a pragmatic stopping point rather than an exhaustive guarantee.
2. **Explain zero-content adoptions** — for every `[BORROWED]` object with zero own attrs/TS/forms/interceptors, run the **reference finder** ([docs/reference-finder.md](docs/reference-finder.md)) to find the technical reason it was adopted (composite-type reference vs. code/query reference) or confirm it has none (candidate for exclusion).
3. **Group into functional blocks** — objects that are `[OWN]` (fully new) or `[BORROWED]` with real own content rarely stand alone; group them by the business scenario they implement (e.g. "outgoing document registry", "personal-cabinet integration", "RIB exchange"). This step is currently manual — read the code and follow cross-references. Where `1c-graph-metadata-mcp` is exposed, route each question through the table in "MCP usage" below (call arguments — `content/skills/1c-impact/SKILL.md`); `onec-hbk-bsl-*`'s `bsl_callers`/`bsl_callees` remain an alternative for call tracing where that server is exposed. **A register reached by two or more objects' code is a grouping candidate, not a conclusion** — check whether each access sits inside a `#Вставка` block (see the registry rule in step 1) before treating the shared register as the extension's link between those objects. Forms of the extension — the offline `1c-form-info` tool (see "MCP usage" below).

   **Before reading code from scratch, check [docs/metadata-modification-patterns.md](docs/metadata-modification-patterns.md)** — a reference of the recurring reasons each metadata type tends to get touched (e.g. an `InformationRegister` gaining a dimension-gap shadow copy, an `ExchangePlan` getting scoped/filtered replication, a `DefinedType` growing to cover a new own object). It speeds up recognizing *why* an object was likely adopted/changed — it does not replace reading the object's actual code before writing the reason into the report.

   **For every wholly-new `Report`/`DataProcessor` with an SKD-only schema (no `ObjectModule`/`ManagerModule` code), read its DCS query — or run `dcs-query-fields-extractor`** ([docs/dcs-query-fields-extractor.md](docs/dcs-query-fields-extractor.md)) **— *before* assigning it to a functional block.** A shared name suffix says nothing about what a report does — its query may read data unrelated to the objects it is named like. Group by what the query actually reads, not by name similarity with other objects in the extension.

   **Exchange-plan / RIB participation is a requirement of the owning block, not a separate infrastructure block.** When an object already belongs to a functional block by its own business purpose, and that same object also participates in an exchange plan — listed in `Ext/Content.xml`, or registered/filtered by code (a registration-rules handler, a hardcoded dispatcher, a registration-settings helper) — describe that participation as part of *that block's* requirements. Do not carve out a standalone "exchange mechanism" / "RIB filter" node to hold it, even when the registration code is physically shared across several blocks (one dispatcher, one common registration-settings module). A shared module or dispatcher does not make a shared requirement: each block's objects usually have their own describable registration path — a dedicated insertion into the typical registration-settings channel, or their own branches in a shared fallback dispatcher, which stay attributable to the block they serve. Splitting a shared mechanism's description across the blocks it actually serves — instead of centralizing it in an artificial node — keeps every requirement traceable to the business need that created it, and lets each block's update risk be assessed on its own evidence instead of one blended risk statement. The **only** thing that legitimately stays a cross-cutting note instead of living inside a block is the shared mechanism's own recurring-maintenance risk, and only when there is concrete evidence for it (e.g. version-marker comments proving the mechanism has already been revised more than once) — record that in the report's risk section (see skeleton §7 below), not as its own functional-block subsection.
4. **Find uniform code patterns** — when several documents/objects look like they implement the same customization independently, search for a shared signature (a region name, a distinctive procedure name) across all `ManagerModule.bsl`/`ObjectModule.bsl` files to confirm the pattern is genuinely uniform and to catch any object that implements it but was missed in step 3. If `onec-hbk-bsl-*` (or an equivalent BSL symbol-index MCP — `1c-code-metadata-mcp`'s `compact_symbol(name=...)` is equivalent for this) is exposed, prefer `bsl_find_symbol(name=..., limit=<enough to cover every hit>)` / `compact_symbol` over `Grep` for this — it returns every definition of a same-named procedure across the whole workspace with exact `file_path`/`line` in one structured call, instead of a text match you still have to de-duplicate by hand. **Either way, a matching interceptor/procedure name is a starting point, not a conclusion** — read the actual body of every matched object before asserting they all share the implementation. One of many siblings sharing an interceptor name can call a completely different — even broken — mechanism, and a conclusion drawn from the name alone is then contradicted by that unread body. Enumerating candidates is not the same as confirming they are the same pattern — only reading each body does that.
5. **Completeness sweep before writing conclusions** — cross-check every object that has *any* `Ext` subfolder (real code/forms/templates) against what step 3 already classified. `bsl_meta_collection(collection="Справочники" | "Документы" | ...)` (if exposed) gives a fast one-call inventory per metadata type to check nothing was missed. Do not declare the analysis complete on the strength of "the customer described N reasons" alone — enumerate every object with real content and make sure each one lands in a named block, a "confirmed no effect" note, or an explicit open question. This is the step that most often finds forgotten reports, disabled data processors, and orphaned print templates.

   **The closure gate is the change registry's `Блок` column, not the object list.** "Every object landed somewhere" is not sufficient — walk every row of step 1's change registry and confirm `Блок` is filled (or explicitly marked unassigned, per report skeleton §7 below) before the analysis counts as complete. An object with all-but-one of its rows assigned is not "done" — the one empty row is exactly the kind of thing this gate exists to catch.

   **Run the semantic-bug sweep before writing conclusions, not instead of reading code.** A full line-by-line reading pass does not scale to hundreds of objects, and a `grep`-scale pass over the same tree misses semantic defects that still parse as valid BSL. Run the four narrow checkers over the whole extension tree as a mechanical supplement:

   - `1c-enum-value-checker` — enum-value literals referencing a value the enum does not have.
   - `1c-defined-type-dispatch-checker` — per suspected dispatch routine, a `DefinedType` member not handled by any branch.
   - `1c-broken-metadata-path-checker` — hardcoded `"Тип.Имя.Форма..."` literals referencing an object that does not exist.
   - `1c-dead-code-after-insert-checker` — a top-level unconditional `Возврат` shadowing typical code or the extension's own code that follows it.

   Every finding is still a candidate, not an automatic report entry — confirm each one against the actual source before writing it into section 2 or 4, same as any other finding in this workflow.
6. **Write the report** using the section skeleton below.

## Report skeleton

A finished analysis is a single Markdown file with these sections, in order:

| # | Section | Content |
|---|---|---|
| 0 | Исходные данные от заказчика | Verbatim customer input, numbered as given |
| 1 | Общие сведения о расширении + Метод анализа | Configuration/extension identity, platform version, and an explicit methodology note (what "adopted" vs "own" means, per-child `ObjectBelonging`, not just open `ChildObjects`) |
| 2 | Функциональные блоки и причины модификации | One numbered subsection per functional block found in step 3; dedicate a subsection to any single object worth a deep dive; flag obsolete/candidate-for-removal findings explicitly in the subsection title. If a block's own objects participate in an exchange plan (RIB or otherwise), describe that as a named part of *this* subsection (e.g. an "exchange mechanism" paragraph) — do not create a separate cross-block subsection for it (see step 3's exchange-plan rule) |
| 3 | Сводная таблица изменённых объектов | One row group per object type, cross-referencing the relevant `2.x` subsection |
| 4 | Не подтверждено / требует уточнения у автора расширения | Every object adopted with zero real content, with its reference-finder verdict; use blockquotes to record items that started here and were later closed |
| 5 | Вопросы к заказчику для следующего раунда обсуждения | Only genuinely open questions — a question closed by evidence found later in the same session must be moved into a blockquote here (or into the relevant `2.x`/`4` section) and removed from the numbered list; renumber after every removal |
| 6 | Итоговый вывод | The functional blocks restated as a short list, isolated additions, confirmed-obsolete items, corrections to earlier (wrong) claims |
| 7 | Риски и опасения заказчика при обновлении типовой конфигурации | Only genuine update-time risks, tied to specific objects/mechanisms found in section 2 |

Keep sections 4 and 5 honest: an item stays in "open questions" only while it is genuinely unresolved. As soon as code/reference evidence closes it, move the resolution into the relevant numbered section and strike it from section 5 — do not leave a question in section 5 that the analysis itself has already answered.

**Appendix — change registry.** Include step 1's change registry (`Объект | Механизм | Куда пишет/что читает | Блок`) as a report appendix, not just scratch working material — it is the evidence trail that shows every atomic change was actually accounted for, and lets a reader audit section 2's block assignments against the underlying granular facts instead of taking them on faith. Keep rows collapsed by unique shape (per step 1's dispatcher-decomposition rule) — the appendix should stay a few dozen rows for a mid-sized extension, not hundreds.

**Collapsing rows for the appendix is a write-up step that can silently undo everything step 1 just fixed — verify before collapsing, don't collapse on appearance.** Objects that look alike (same type, same primary interceptor) can still differ by a second own interceptor or own attributes, and one shared appendix line drops those rows although the raw registry has them. The tool being right does not make the write-up right — before folding several objects' rows into one appendix line, re-open each object's *own* full row set (not just its first/primary row) and confirm every single row is actually covered by the shared explanation. One row that doesn't fit means that object gets its own line, never a share of the group's.

**Adopted-object staleness — read before trusting a "declared value" / "composition" result from `1c-enum-value-checker` or `1c-defined-type-dispatch-checker`.** An extension's own copy of an `Adopted` (typical) object can be a stale snapshot with far fewer children than the base configuration currently declares. Both tools resolve this by preferring the base configuration's copy over the extension's own snapshot whenever `-ConfigPath` is given and the object is `Adopted` — **always pass `-ConfigPath` to these two tools**; running without it is a degraded, unverified mode.

## Environment constraints — tool availability is not guaranteed

Both `cfe-diff` and `1c-reference-finder` are Python scripts that need a shell to run. **A subagent invocation can end up with only `Read`/`Write`/`Edit`/`Grep`/`Glob` available, with no working shell and no MCP tools, even when the invoking agent's own configuration lists `Bash`/`MCP` among its tools.** Check for a working shell at the very start of a run (attempt a trivial command) rather than assuming it and discovering the failure mid-workflow. If no shell is available:

- Do the per-child `ObjectBelonging` check from step 1 by direct `Read`/`Grep` of the metadata XML (same logic `cfe-diff -Mode A` implements — see `content/skills/1c-metadata-manage/tools/1c-cfe-manage/scripts/cfe-diff.py` for the exact algorithm if in doubt).
- Do the reference search from step 2 by `Grep` for the object's Ref-type token and manager/query-style Cyrillic name across the extension tree (same logic `reference-finder.py` implements — see [docs/reference-finder.md](docs/reference-finder.md)).
- State plainly in the report's methodology section (section 1) that the check was performed manually because no shell tool was available, not because of a missing Python dependency — these are different failure modes and the report should not conflate them.

## MCP usage

This is analysis work, not a BSL/metadata edit — the BSL validation gates of `content/rules/verification-gates.md` (`syntaxcheck`/`check_1c_code`/`review_1c_code`) do not apply. Use the project's search/graph MCP tools (`content/skills/mcp-1c-tools/SKILL.md`, `content/rules/mcp-first-search.md`) for step 3 (grouping into functional blocks) and to verify claims about base-configuration behavior before writing them into the report, per `content/rules/sdd-integrations.md`'s evidence discipline — every metadata name, attribute, or platform behavior asserted in the report should be grounded in a source you actually checked, not assumed from a similar-looking object.

### `onec-hbk-bsl-*` BSL static-analysis MCP servers — what to use and what not to

Some projects expose a BSL language-server-backed MCP pair, one instance per workspace root (e.g. `onec-hbk-bsl-main` over the base config, `onec-hbk-bsl-ext` over the extension) — check `.mcp.json` for the exact server names. The pairing suits extension-vs-base comparison, but the tools differ in what they can be trusted for — do not go by tool descriptions alone.

**Use:**

- **`bsl_find_symbol(name, limit)`** — returns every definition of a same-named procedure/function across the whole workspace with exact `file_path`/`line`. **This is the correct tool for step 4's "read the actual body of every matched object" requirement** — enumerate with `bsl_find_symbol` first, then read each file it lists.
- **`bsl_meta_collection(collection, limit)`** — one-call inventory of every object in a metadata collection (`"Справочники"`, `"Документы"`, `"РегистрыСведений"`, …). Good for step 5's completeness sweep.
- **`bsl_diagnostics(file_path, include_unused=true)`** — a real BSLLS-compatible diagnostic engine, including a `BSL-DEAD` (unused non-export routine) check. Useful as a fast first-pass scan across many modules before manual reading — but treat `BSL-DEAD` hits on interceptor procedures (`&Перед`/`&После`/`&ИзменениеИКонтроль` targets) as needing verification, not fact: the engine may not recognize a directive-bound interceptor as "used" and can false-positive there.
- **`bsl_status`** — trivial index-readiness check, run first.
- **`bsl_callers`/`bsl_callees(symbol_name, file_filter)`** — cross-object BSL call tracing, an alternative to the graph server's `trace_call_chain`. When `symbol_name` is shared by several modules the call returns `{"ambiguous": true, "candidates": [{"file", "line", "signature"}, ...]}` instead of picking one; pass `file_filter` (a path substring) to select the intended definition and get its callers/callees with `caller_file`/`callee_file`/`callee_line` resolved. **A callee listed with several same-named candidates is unresolved, not polymorphic** — a qualifier such as `Документы.<Объект>.<Метод>(...)` is not used for resolution; read the call site before describing such a callee.

**`BSL051` (`UnreachableCode`) — partial overlap with `1c-dead-code-after-insert-checker`; run both, do not treat either as a substitute for the other.** `BSL051` fires when the unreachable code sits in an otherwise plain routine with no `#Вставка`/`#КонецВставки` markers, but gives **no** diagnostic when the unreachable code is typical/original logic left dangling right after a `#КонецВставки` marker — the analyzer treats that boundary as breaking its control-flow graph, although the platform executes the code on both sides as one statement sequence. There `include_unused=true` only yields a `BSL-DEAD` "unused function" hit — a **different and misleading** signal (the routine is not unused, it is a directive-bound interceptor; see the `BSL-DEAD` false-positive class above) that says nothing about dead code inside an actively used routine. That is the highest-value case for this skill (typical behaviour silently shadowed by an extension), so `1c-dead-code-after-insert-checker` ([docs/dead-code-after-insert-checker.md](docs/dead-code-after-insert-checker.md)) is not redundant with `BSL051` — `BSL051` is the faster first pass, the offline tool covers the `#Вставка`-adjacent case.

**No BSL-LS rule overlaps `1c-enum-value-checker`, `1c-defined-type-dispatch-checker`, or `1c-broken-metadata-path-checker`.** None of the public rules (`bsl_list_rules`) covers these defects: the engine has no notion of enum-value existence, `DefinedType` composition completeness, or metadata-path string validity. `1c-syntax-checker-mcp`'s `syntaxcheck` cannot cover these either — it takes a bare code string with no workspace/metadata context, so it cannot resolve enum values, `DefinedType` members, or object existence in the first place. All three tools are additive, not overlapping.

**Do not use as a substitute for this skill's core checks:**

- **`bsl_meta_object(name)` does not distinguish `ObjectBelonging=Adopted` from own attributes.** It reports the object's structure as such — the same attribute list against the extension's index and against the base configuration's own index (`onec-hbk-bsl-main`), with no adoption flag. **Using it in place of `cfe-diff -Mode A` / the per-child `ObjectBelonging` check would silently reintroduce the exact "open `ChildObjects` ≠ new attribute" mistake this skill exists to prevent.** It may still be useful for a quick shape overview, but never cite its attribute list as evidence of what the extension added.
- **`bsl_references(symbol_name)` only indexes BSL code, not XML metadata type declarations.** Composite-type references inside other objects' XML (`CatalogRef.X` in dimension/attribute `<Type>` elements) are invisible to it, so it cannot see the "composite-type reference" mechanism from `content/skills/1c-extension-analysis/docs/reference-finder.md` — at most it supplements the "code/query reference" half, and only for BSL text; do not rely on it for queries embedded in DCS XML.

Net effect: this MCP pair is a genuine accelerant for steps 4 and 5 (pattern enumeration, collection inventory, fast dead-code scanning) but **does not replace** `cfe-diff -Mode A` / `reference-finder.py` for steps 1–2 (the `ObjectBelonging` and reference-mechanism checks) — those remain the authoritative source for "was this added by the extension" questions.

### `1c-code-metadata-mcp` — limits for this workflow; prefer the offline `1c-form-info`

Not part of every deployment — check `.mcp.json`; tool catalogue: `content/skills/mcp-1c-tools/docs/1c-code-metadata-mcp.md`. It indexes the base configuration together with the discovered extensions, but its artifact tools answer from the base layer only:

- **Does not answer `ObjectBelonging`.** `get_metadata_details(...)` returns an object's attribute list without an adoption flag, whatever the scope or `origin`, and without the attributes the extension added. `cfe-diff -Mode A` / the per-child `ObjectBelonging` check remain the only authoritative source for "did the extension add this".
- **Artifact tools do not see what the extension added.** `get_report_artifact` does not find a report the extension added, and `get_role_artifact` does not list rights declared in the extension's adopted roles. Use the graph server's `get_report_dcs_lineage` / `get_access_rights` instead.
- **`compact_symbol(name=...)` serves step 4** — it returns every same-named definition across base and extension with an exact line range; a substitute for `bsl_find_symbol` where `onec-hbk-bsl-*` is not exposed.
- **Form layout — the offline `1c-form-info` tool** (`content/skills/1c-metadata-manage/tools/1c-form-info/scripts/form-info.py`, documented in `content/skills/1c-metadata-manage/docs/form-manage.md`), not `inspect_form_layout`: it renders the element hierarchy with each handler attached to its element, typed attributes, and form commands/parameters.

Net effect: do not route steps 1–3 through this server. `compact_symbol` is the one call worth using (step 4). A deployment that does not ship it loses nothing this workflow depends on.

### `1c-graph-metadata-mcp` — what extension analysis adds to `1c-impact`

The server is not part of every deployment — check `.mcp.json`. Calls and arguments are not repeated here: usages, call chains, register writers, `compare_base_and_extension` and `resolve_effective_entity` — `content/skills/1c-impact/SKILL.md`; forms — `content/skills/1c-form-inspect/SKILL.md`; rights, event subscriptions, DCS lineage, data links and the base/extension layer contract — `content/skills/mcp-1c-tools/docs/1c-graph-metadata-mcp.md`. This section maps the workflow's questions to those tools and adds what matters for an extension.

| Workflow question | Tool | For extension analysis |
|---|---|---|
| Base vs extension for one object (steps 1, 5) | `compare_base_and_extension` | A cross-check of `cfe-diff -Mode A` — see below |
| Which layer's variant of an object or routine is effective | `resolve_effective_entity` | Wrapping and extending variants across the layers; a source conclusion, not proof of what a running infobase executes |
| Who calls / what a routine calls (step 3) | `trace_call_chain` | Follows calls into manager modules, including methods the extension added to its own object's manager module, and into base common modules |
| Where an object is used as a type (step 2) | `find_usages_of_object`, `get_data_links` | `get_data_links` also names the attribute that carries each link |
| Code that reads or writes a register (step 3) | `find_object_referrers` with `object_name` | Registers only: a document or catalog answers empty without a warning. One representative file:line per (object, access). Counts the copied typical body of `&ИзменениеИКонтроль` |
| Registers reached by ≥2 objects (step 3) | `find_object_referrers` with `min_referrers=2`, no `object_name` | Grouping candidates, dominated by base code — keep the extension's hits, read `truncated` / `exhaustive`, confirm each access against `#Вставка` ranges |
| Role rights, including the extension's adopted roles | `get_access_rights` | Covers `reference-finder`'s role gap; `Документ.X` and `Справочник.X` answer separately |
| A report's DCS query, fields, parameters | `get_report_dcs_lineage` | Includes reports the extension added; an alternative to `dcs-query-fields-extractor` |
| Event subscriptions and their sources | `get_event_subscriptions` | Includes the extension's own subscriptions |
| Enum values | `search_metadata` with `{"operation": "list_enum_values", "object_name": "<Имя>"}` | Not `find_predefined_values` — it reads predefined items only and answers empty for an enum |
| Bindings and handlers of the extension's forms | offline `1c-form-info` | See «Forms» below |
| Inventory of the whole extension | `cfe-diff -Mode A` | Not `compare_graph_scope(extension_ref=...)`: on a real extension it runs into the tool timeout, narrowed or not |
| Exchange-plan composition | `1c-exchangeplan-content` | No MCP tool parses `Ext/Content.xml` |

**Attributing a hit to the extension.** With the base and the extension as layers of one project, `trace_call_chain`, `find_object_referrers` and `get_access_rights` answer across both layers. A hit belongs to the extension only when its file lies in the extension dump — and, inside an `&ИзменениеИКонтроль` routine, only within a `#Вставка` block. An adopted object or role exists in both layers, so a call naming it can answer `ambiguous` with a `candidates` list: pass the chosen candidate's `node_id` as `object_name` (or `role`) — `find_object_referrers` and `get_access_rights` accept it. General rule for ambiguous entities — `content/skills/mcp-1c-tools/docs/1c-graph-metadata-mcp.md → Contract and scope`.

**`compare_base_and_extension(object_name, extension_name)`** lists, per object, the attributes, forms and routines taken from the base, overridden or added by the extension; a routine appears in one of these groups only. `extension_name` is the layer name — the `Name` in the extension's own `Configuration.xml`, not the directory it was dumped into; a directory name finds nothing. It compares the layers as two node sets by name, independently of `cfe-diff -Mode A`'s XML reading — cross-check the two. `search_metadata({"operation": "list_extension_objects", "extension_name": ..., "extends_type": "added"})` lists the extension's new top-level objects separately from the adopted ones. The comparison covers attributes, forms and routines only: roles, RLS, subsystem composition and command-interface changes are outside it, and an empty "Формы" section for one object says nothing about form overrides elsewhere — step 5's completeness sweep stays mandatory.

**Forms.** Graph form nodes are keyed by name without the owner's category: when the extension carries two objects of different categories with one name (`Справочник.X` and `Документ.X`), `find_form_links` and `get_form_structure` return the forms of both merged into one answer. The offline `1c-form-info` reads the `Form.xml` itself and has no such ambiguity — use it for the extension's forms.
